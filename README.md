# SKALA Vue.js 실습 — 판교 5반 임채환

전국 주요 도시의 날씨를 보여주는 대시보드를 만들면서, 1일차부터 배운 문법을 회차마다 쌓아 올린 실습 기록입니다.

- 소스코드: <https://github.com/chaexove-ai/skala_vue>
- 배포 주소: <https://skala-vue-r5p7.vercel.app/>

## 제출자

- 캠퍼스: 판교
- 이름: 임채환
- 반: 5반
- 번호: P163

## 사용 스택

- **Vue 3** (Composition API) + **Vite**
- **Vue Router 4** — 지연 로딩, 동적 경로 매칭, Catch-all Route, 전역 네비게이션 가드
- **Pinia** — 날씨 단위(섭씨/화씨) 설정과 대시보드 화면 상태를 화면 간에 공유
- **Axios** — OpenWeatherMap · OpenStreetMap 등 외부 REST API 호출
- **Leaflet** — 상세 페이지 지도 (OpenStreetMap 타일 + 날씨 레이어)
- **Element Plus** — 입력 검증·알림·확인창 등 상호작용 컴포넌트 (주문형 로딩)
- **ESLint · Prettier** — 코드 품질과 포맷 통일

## 실행 방법

```bash
npm install
npm run dev
```

실행 후 `http://localhost:5173` 접속.

4일차 실습부터 외부 날씨 API를 호출하므로, 프로젝트 루트에 `.env` 파일을 만들고 본인 키를 넣어야 합니다. (`.env.example` 참고, `.env`는 저장소에 올라가지 않습니다)

```
VITE_OPENWEATHER_KEY=본인_OpenWeatherMap_API_키
```

## 1일차

### 1. SampleOne — 반응형 데이터 (Reactivity)

일반 변수(let)와 `ref()`로 감싼 반응형 변수를 각각 버튼으로 증가시키면서, 일반 변수는 화면의 숫자가 변경 되지 않고 ref 변수만 버튼을 누르는 순간 화면에 반영되는 차이를 확인했습니다.

**느낀점**: 저는 원래 html/css에 익숙해서 화면 값을 바꾸려면 무조건 JS로 직접 innerHTML이나 textContent를 다시 써줘야 하는 게 당연했는데, ref로 감싼 변수는 그냥 값만 바꿨을 뿐인데 화면이 알아서 갱신되는 게 제일 신기했습니다. 반대로 일반 변수(let)는 콘솔에 찍어보면 값은 분명히 바뀌어 있는데 화면엔 반영이 안 돼서, "Vue가 감시하고 있는 변수"와 "그냥 JS 변수"가 따로 있다는 걸 처음 체감했습니다.

### 2. SampleTwo — Text Interpolation

`{{ }}` 안에 문자열뿐 아니라 `.toUpperCase()`, `.length`, 산술 연산, 삼항 연산자 같은 JS 표현식을 그대로 써서 렌더링해봤습니다.

**느낀점**:표현식이 들어간다는 것보다, 넣으면 안 되는 게 뭔지가 더 눈에 들어왔습니다. 실습 코드에 {{ 'Random number: ' + Math.ceil(Math.random() * 100) }}가 있는데, 이건 화면이 다시 그려질 때마다 값이 새로 나옵니다. 옆에 있는 버튼을 눌러 다른 데이터를 바꾸면 이 숫자까지 같이 바뀌는 셈이라, 템플릿에는 몇 번을 계산해도 같은 값이 나오는 것만 두는 게 맞겠다 싶었습니다

### 3. VueHtml — v-html

문자열에 담긴 HTML 태그를 실제 엘리먼트로 렌더링하는 `v-html`과, 그냥 텍스트로만 출력되는 일반 보간법의 차이를 비교했습니다.

**느낀점**:원래 HTML 파일에 텍스트로 <span>빨간 글자</span>를 쓰면 당연히 그대로 렌더링되는데, 여기선 그 텍스트가 스트링이라는 이유만으로 그냥 두면 화면에 <span>...이라는 글자 그대로 찍혔습니다. v-html을 붙여야 진짜 태그로 해석된다는 걸 보고, "아 문자열이랑 HTML은 Vue 입장에선 다르게 취급되는구나"를 처음 느꼈습니다.

### 4. VueHtmlXss — v-html과 XSS

입력창에 악성 스크립트가 담긴 HTML을 넣고 `v-html`로 그대로 렌더링했을 때 실제로 스크립트가 실행되어 페이지 이동까지 발생하는 걸 확인했습니다.

**느낀점**:태그가 렌더링되는 것 자체는 innerHTML 쓰면서 익숙했던 일이라 새로울 게 없었는데, 눈에 들어온 건 Vue가 기본값을 어디에 뒀느냐였습니다. {{ }}는 뭘 넣든 글자로 처리하고, 태그로 해석하려면 v-html이라는 이름이 다른 디렉티브를 굳이 골라 써야 합니다. 위험한 쪽을 기본에서 빼놓고 쓰려면 이름을 대고 쓰라는 식이라, 실수로 뚫리는 게 아니라 알고도 쓴 게 되는 구조입니다. 결국 문제는 문법이 아니라 어디에 쓰느냐라, 관리자가 작성한 공지처럼 출처가 내 쪽인 값에만 쓰고 사용자가 친 값은 {{ }}로 두면 되는 거였다는걸 배웠습니다.

### 5. VueText — v-text

`v-text`가 `element.innerText`와 동일하게 동작해서, `v-html`과 달리 태그가 해석되지 않고 그대로 문자로 출력되는 걸 확인했습니다.

**느낀점**:슬라이드에서 실무에서는 v-text 대신 Text Interpolation을 쓴다는 설명을 보고 실습하면서, 이 디렉티브가 왜 존재하는지보다 왜 잘 안 쓰이는지를 실습을 통해 거꾸로 이해하게 됐습니다.

### 6. VueBind — v-bind 기본

`:href`, `:src`, `:disabled`로 링크 주소, 이미지 경로, 버튼 비활성화 여부를 변수에 동적으로 연결했습니다.

**느낀점**:HTML에서 href나 src는 늘 고정된 문자열만 쓰던 감각이 있었는데, 직접 :href="dynamicUrl"로 링크를 걸어보니까 콜론 하나 차이로 고정값과 동적인 값이 구분된다는 게 실습하면서 확 와닿았습니다. 콜론을 빼먹고 그냥 href="dynamicUrl"이라고 쓰면 그대로 문자열 취급돼서 링크가 깨지는 것도 직접 실수해보고 알았습니다.

### 7. VueBindClass — v-bind 클래스 바인딩

객체 형식(`{'클래스명': 조건}`)과 배열 형식(`[클래스, 조건 ? A : B]`) 두 가지 방식으로 조건에 따라 클래스를 동적으로 붙이고 뗐습니다.

**느낀점**:{'text-danger': isWarning} 객체 하나만 넣었더니 버튼 누를 때마다 클래스가 알아서 붙었다 뗐다 하는 게 실습하면서 제일 편하게 느껴졌습니다. 배열 형식으로 여러 클래스를 한번에 조립하는 것도 직접 해보니 생각보다 간단했습니다.

### 8. VueBindStyle — v-bind 스타일 바인딩

인라인 스타일을 객체/배열 형태로 바인딩하고, 숫자 입력값을 `px` 단위 문자열로 변환해 박스 크기를 실시간으로 바꿔봤습니다.

**느낀점**:인라인 스타일은 늘 style="color: red"처럼 문자열로 쓰는 줄만 알았는데, 여기선 객체로 넣으면서 font-size를 fontSize로 써야 했습니다. 평소 쓰던 CSS 속성 이름 그대로 썼다가 안 먹혀서 왜 안 되나 한참 찾아보며 공부했습니다.

### 9. VueBindShorthand — v-bind 단축 문법

Vue 3.4에서 추가된, 변수명과 속성명이 같을 때 `:id="id"`를 `:id`로 줄여 쓰는 문법을 사용해봤습니다.

**느낀점**::src 하나만 쓰고 값을 생략하는 게 처음 쳐볼 땐 뭔가 빠뜨린 것 같은 기분이었는데, 몇 번 반복해서 쓰다 보니까 정말 편한 기능인거 같다는 생각이 들었습니다.

### 10. VueIf — v-if / v-else-if / v-else

로그인 상태를 토글하는 스위치와, 점수 구간에 따라 A/B/C/F 학점을 나눠 보여주는 다중 조건 분기를 구현했습니다.

**느낀점**:점수 구간에 따라 div 네 개를 v-if / v-else-if / v-else로 나란히 연결해보니, 점수를 바꿀 때마다 딱 하나의 div만 조건에 맞게 화면에 남는 게 실습하면서 확실히 눈에 들어왔습니다. 로그인 상태 토글도 버튼 하나로 문구가 바로 바뀌는 걸 보니 생각보다 코드가 깔끔하게 나왔습니다.

### 11. VueShow — v-show

조건이 false가 되어도 DOM에서 사라지지 않고 `display: none`만 붙는 `v-show`의 동작을, 개발자도구 Elements 탭에서 직접 확인했습니다.

**느낀점**:버튼을 숨기려면 원래 CSS로 display: none 클래스를 미리 만들어두고 JS로 토글하는 식이었는데, v-show는 그런 클래스 없이 조건 하나만 넣으면 알아서 display: none이 붙었다 없어졌다 하는걸 경험했습니다. v-if랑 헷갈렸는데 개발자도구 열어서 보니 태그가 아예 사라지는 v-if랑 다르게 v-show는 DOM에 그대로 남아있는 게 차이였습니다.

### 12. VueFor — v-for

배열, 객체, 배열 속 객체 세 가지 데이터 형태를 각각 반복 렌더링하고, 매번 `:key`를 고유 값으로 바인딩했습니다.

**느낀점**:원래 HTML이었으면 <li>를 개수만큼 하나하나 복사 붙여넣기 해야 했을 텐데, 배열 하나 두고 v-for 한 줄만 쓰니까 저장하는 순간 li 세 개가 자동으로 쫙 찍혀 나와서 너무 편했습니다. key를 꼭 같이 넣어야 하는 이유도 배열/객체/배열 속 객체 세 가지를 다 실습해보면서 자연스럽게 체감됐습니다.

### 13. VuePre — v-pre

`v-pre`가 붙은 영역은 Vue 컴파일러가 해석하지 않고 `{{ }}`를 그대로 텍스트로 보여준다는 걸 확인했습니다.

**느낀점**:{{ }}가 자동으로 해석되는 게 하도 당연해져서, 반대로 이걸 안 풀고 그대로 글자로 보여주고 싶을 땐 v-pre라는 걸 따로 붙여야 한다는 게 오히려 신선했습니다. 문서에 Vue 코드 예제를 그대로 보여줄 때 쓰는 용도라는 설명 듣고 나니 왜 필요한지 납득이 갔습니다.

### 14. VueCloak — v-cloak

데이터 바인딩이 끝나기 전 잠깐 `{{ }}` 원본 텍스트가 노출되는 현상을, `v-cloak` + `[v-cloak] { display: none !important }` CSS 조합으로 막는 방법을 실습했습니다.

**느낀점**:이미지 로딩 느릴 때 깨진 화면이 잠깐 보이는 것과 비슷한 문제라고 이해는 했는데, 로컬 환경이라 네트워크가 빨라서 실습만으로는 {{ message }} 깜빡임을 직접 눈으로 보긴 어려웠습니다. 그래도 [v-cloak] 속성 선택자로 그 구간을 미리 숨겨두는 CSS 트릭 자체는 실습하면서 재밌었습니다.

### 15. VueOnce — v-once

`v-once`가 붙은 요소는 최초 한 번만 렌더링되고, 이후 데이터가 바뀌어도 화면이 갱신되지 않는 걸 일반 변수와 비교해서 확인했습니다.

**느낀점**:v-once가 붙은 숫자는 버튼을 아무리 눌러도 그대로 있고, 바로 옆에 있는 일반 변수 숫자만 계속 올라가는 걸 나란히 비교해보니까 딱 한 번만 렌더링하고 멈춘다는 게 실습으로 확실히 눈에 들어왔습니다.

### 16. VueMemo — v-memo

`v-memo="[name]"`로 지정한 변수(name)가 바뀌지 않으면, 다른 변수(age)가 바뀌어도 캐시된 화면을 그대로 재사용하는 동작을 확인했습니다.

**느낀점** :v-memo="[name]"으로 감시할 값을 지정해두니까 age 버튼을 아무리 눌러도 화면이 그대로 있다가, name을 바꾸는 순간에만 같이 갱신되는 걸 직접 눌러보면서 확인했습니다. 지정한 값 하나만 감시한다는 게 정확히 어떤 느낌인지 실습해보고 나서야 확실히 이해됬던거 같습니다.

## 2일차

### 📁 practices/basic

### 1. EventBasic — v-on 이벤트 핸들링 기초

`@click="count++"`처럼 인라인으로 바로 연산을 넣는 방식과, `@click="showAlert"`처럼 스크립트에 정의해둔 함수를 호출하는 방식 두 가지를 각각 버튼에 연결했습니다.

**느낀점** :예전에 addEventListener로 붙여놓고 removeEventListener를 빠뜨려서 클릭 한 번에 같은 동작이 두 번 실행되거나, 요소는 없어졌는데 리스너만 남아 있던 적이 있었습니다. 그래서 이벤트는 붙이는 것보다 떼는 걸 신경 써야 하는 일이라고 생각하고 있었는데, @click은 태그에 적어두면 그 태그가 사라질 때 같이 정리되니 뗄 걱정을 할 일이 없었습니다. 붙이고 떼는 시점을 내가 관리하다가 요소의 수명에 맡기게 된 셈이라, 이게 선언형으로 쓴다는 말의 실제 이득이구나 싶었습니다.

### 2. EventObject — 이벤트 객체($event) 활용

아무 인자 없이 이벤트를 받는 함수로 `e.clientX/clientY` 클릭 좌표를 확인하고, 커스텀 인자와 함께 `$event`를 명시적으로 넘기는 함수로 `e.target.tagName`을 함께 확인했습니다.

**느낀점**: 순수 JS에서 `onclick="handler(event)"`처럼 이벤트 객체를 넘기던 것과 비슷하게, Vue에서도 다른 인자와 같이 쓸 때는 `$event`를 명시적으로 넘겨줘야 한다는 걸 실습하면서 알게 됐습니다. 인자 없이 이벤트만 받는 함수는 클릭 좌표를 바로 꺼내 쓸 수 있어서 편했고, `$event`를 다른 인자랑 같이 넘기는 순서는 처음에 헷갈려서 콘솔 찍어가며 확인했습니다.

### 3. EventModifier — 이벤트 수식어(Modifiers)

링크 클릭 시 기본 이동 동작을 막는 `.prevent`, 그리고 자식에서 부모로 이벤트가 전파되는 걸 막는 `.stop`을 버튼 두 개(하나는 stop 적용, 하나는 미적용)로 비교했습니다.

**느낀점**: 원래 JS였다면 함수 안에서 `e.preventDefault()`나 `e.stopPropagation()`을 직접 호출해야 했는데, Vue에서는 `@click.prevent`, `@click.stop`처럼 템플릿에 수식어만 붙이면 끝나는 게 코드가 훨씬 간결해진다고 느꼈습니다. 특히 `.stop`을 안 붙인 자식 버튼을 눌렀을 때 부모의 클릭 핸들러까지 같이 실행되는 걸 직접 보고 나서야 버블링이 뭔지 확실히 이해됐습니다.

### 4. ModelBasic — v-model의 동작 원리

`v-model` 축약 문법으로 바인딩한 값과, 이를 풀어쓴 `:value` + `@input` 조합으로 바인딩한 값을 나란히 두고 동일하게 동작하는지 비교했습니다.

**느낀점**: v-model이 그냥 마법처럼 양방향 바인딩을 해주는 줄만 알았는데, 직접 `:value="text2"`랑 `@input="(e) => (text2 = e.target.value)"`로 풀어서 만들어보니까 v-model이 사실 이 두 가지를 합쳐놓은 축약 문법이었다는 걸 실습을 통해서 알게 됐습니다.

### 5. ModelForm — 다양한 Form 요소와 v-model

textarea, 단일 체크박스(Boolean), 다중 체크박스(배열), 라디오, select 총 다섯 가지 입력 요소를 각각 v-model로 연결하고 데이터 타입이 요소마다 다르게 저장되는 걸 확인했습니다.

**느낀점**: 체크박스 하나짜리는 true/false로 저장되는데, 여러 개를 묶었을 때는 꼭 배열로 초기화해야 값이 제대로 쌓인다는 걸 처음에 빈 문자열로 뒀다가 에러가 나서야 알게 됐습니다. 같은 v-model인데도 태그 종류에 따라 저장되는 데이터 형태가 다 다르다는 게 실습하면서 제일 인상 깊었습니다.

### 6. ModelModifier — v-model 수식어

입력 확정 시점을 바꾸는 `.lazy`, 문자열을 숫자로 바꿔주는 `.number`, 양끝 공백을 제거하는 `.trim`, 그리고 `.trim.number`를 체이닝해서 동시에 적용하는 경우까지 확인했습니다.

**느낀점**: `.number`를 안 붙였을 때 입력값이 숫자처럼 보여도 사실은 문자열로 저장돼있다는 걸 typeof로 직접 찍어보고 알았습니다. `.trim.number`처럼 수식어 두 개를 한 번에 체이닝해서 공백 제거랑 형변환을 동시에 처리할 수 있다는 것도 편리하다고 느꼈습니다.

### 7. StyleScoped — Scoped 스타일과 외부 CSS

`<style scoped>`로 감싼 스타일은 이 컴포넌트 안에서만 적용되고, 별도의 `<style>` 태그에서 `@import`로 불러온 외부 CSS(`challenge.css`)는 scoped 없이 전역으로 적용되는 차이를 확인했습니다.

**느낀점**: 프론트엔드 디자인을 할 때 CSS 파일 하나에 클래스 이름이 겹치지 않게 신경 써서 짓던 습관이 있었는데, scoped를 붙이면 같은 클래스 이름을 다른 컴포넌트에서 써도 서로 안 겹친다는 걸 실습하면서 알게 됐습니다. 반대로 같은 파일 안에 있어도 scoped 없는 두 번째 style 태그는 전역으로 적용된다는 것도 버튼 색이 그대로 나오는 걸 보고 확인했습니다.

### 📁 practices/composition

### 1. ReactiveRef — ref() 기초

숫자(count), 문자열(name), 불리언(isActive), 배열(items), 객체(user) 다섯 가지 타입을 각각 `ref()`로 감싸서 버튼 클릭·`push`·중첩 프로퍼티 변경(`user.value.name = ...`)으로 반응형이 유지되는지 확인했습니다.

**느낀점**: ref()는 숫자나 문자열 같은 단순 값만 감싸는 줄 알았는데, 객체나 배열을 넣어도 `.value` 뒤에 원래 쓰던 것처럼 `.name`, `.push()`를 그대로 붙여 쓸 수 있고 반응형이 그대로 유지된다는 걸 실습하면서 확인했습니다.

### 2. ReactiveReactive — reactive() 기초

`reactive()`로 객체(userReactive)와 배열(items)을 각각 선언해서, 객체는 나이 증가 버튼으로, 배열은 `push`/`splice`로 항목을 추가·삭제하며 반응형 동작을 확인했습니다.

**느낀점**: reactive()는 `.value` 없이 바로 `userReactive.age++`처럼 접근한다는 점이 ref()랑 제일 다르게 느껴졌습니다. 배열도 `splice`로 특정 인덱스만 지워도 화면이 바로 갱신되는 걸 보면서, 객체·배열처럼 덩어리진 데이터는 reactive()가 더 자연스럽겠다는 생각이 들었습니다.

### 3. ComputedBasic — computed() 캐싱 동작 비교

count에 의존하는 일반 함수(getMethodResult)와 `computed()`(doubleCount)를 나란히 두고, count와 무관한 dummy 변수를 증가시켰을 때 일반 함수는 화면이 리렌더링될 때마다 콘솔 로그를 매번 찍으며 재실행되지만, computed는 의존성(count)이 안 바뀌면 캐시된 값을 그대로 재사용해서 로그가 안 찍히는 차이를 확인했습니다.

**느낀점**: dummy 버튼을 눌렀을 때 일반 함수 쪽 로그(❌)만 계속 찍히고 computed 쪽 로그(✅)는 안 찍히는 걸 콘솔로 직접 보고 나서야, computed가 "값이 아니라 의존성"을 기준으로 캐싱한다는 말이 실감났습니다.

### 4. WatchersBasic — watch() 단일 소스 감시

currentCity라는 단일 ref를 `watch()`로 감시해서, 버튼으로 도시를 바꿀 때마다 이전 값(oldValue)과 새 값(newValue)을 함께 받아 로그 메시지를 갱신하고, 실무에서 값이 바뀔 때 서버에 다시 요청을 보내는 상황을 콘솔 로그로 시뮬레이션했습니다.

**느낀점**: watch 콜백에 newValue만 오는 줄 알았는데 oldValue까지 같이 넘어온다는 걸 보고, "무엇으로 바뀌었는지"뿐 아니라 "무엇에서 바뀌었는지"까지 알 수 있다는 게 실무에서 왜 유용한지 이해가 됐습니다.

### 5. WatchersMulti — watch() 여러 소스 동시 감시 (Multi-Source Watch)

성(lastName)과 이름(firstName) 두 개의 ref를 배열로 묶어 `watch([lastName, firstName], ...)` 형태로 감시해서, 둘 중 하나만 바뀌어도 콜백 하나가 반응하고 newValues/oldValues도 각 소스와 같은 순서의 배열로 전달되는 걸 확인했습니다.

**느낀점**: watch를 변수마다 따로 하나씩 만들어야 하는 줄 알았는데, 배열로 묶어서 감시 대상 여러 개를 watch 하나로 처리할 수 있다는 걸 확인했습니다. 콜백 인자도 각각 배열로 오다 보니, 어느 인덱스가 어느 변수인지 순서를 맞춰서 구조분해해야 한다는 점을 신경 쓰게 됐습니다.

### 6. WatchersDeep — watch() Deep Watch

객체(user)를 감싼 ref를 `{ deep: true }` 옵션으로 감시해서 name이나 age 어느 속성이 바뀌어도 전체를 감지하는 방법과, 화살표 함수로 `user.value.age`만 콕 집어 감시해서 이전 값과 새 값을 정확히 구분해 추적하는 방법 두 가지를 비교했습니다.

**느낀점**: `watch(user, ...)`만 써놓고 `{ deep: true }`를 안 붙이면 콜백이 아예 발동하지 않는다는 걸 알고 나니, 객체 내부 속성 변경까지 감시하려면 deep 옵션이 필수라는 걸 체감했습니다. 대신 속성 하나만 콕 집어 감시하는 방식은 oldAge/newAge가 정확히 구분돼서 나온다는 차이도 비교하면서 알게 됐습니다.

### 7. WatchersReactive — reactive 데이터 watch 규칙

`reactive()`로 만든 state 객체를 통째로 `watch(state, ...)`로 감시하면 deep이 자동 적용되지만 newVal과 oldVal이 똑같이 나오는(과거 값이 보존되지 않는) 함정과, `watch(() => state.price, ...)`처럼 특정 속성만 콕 집어 감시하면 과거 값이 정상적으로 보존되는 차이를 비교했습니다.

**느낀점**: state 전체를 감시했을 때 이전 가격과 현재 가격이 똑같이 찍히는 걸 보고 처음엔 코드가 잘못된 줄 알았는데, reactive 객체는 프록시라서 oldVal이 사실 newVal과 같은 참조를 보고 있다는 설명을 듣고서야 왜 그런지 이해했습니다. 그래서 과거 값이 진짜 필요할 땐 속성 하나만 화살표 함수로 콕 집어 감시해야 한다는 걸 알게 됐습니다.

### 8. WatchersWatchEffect — 자동 감시자 watchEffect()

감시 대상을 따로 지정하지 않고, 콜백 내부에서 사용한 username과 age를 Vue가 자동으로 추적하는 `watchEffect()`를 실습했습니다. `watch()`와 달리 화면이 처음 마운트되는 순간 콜백이 즉시 한 번 실행된다는 점도 함께 확인했습니다.

**느낀점**: watch()는 감시할 대상을 첫 번째 인자로 꼭 지정해야 하는데, watchEffect()는 그런 지정 없이 콜백 안에서 쓴 변수를 알아서 감시 목록에 등록한다는 게 처음엔 편하다고만 느껴졌습니다. 그런데 슬라이드 설명을 들어보니, 값이 바뀌지 않아도 컴포넌트가 처음 만들어지는 순간 무조건 한 번 즉시 실행되고, 오직 함수 내부에서 실제로 접근한 반응형 데이터만 감시 대상으로 자동 등록된다는 특징이 있었습니다. 감시 대상을 따로 적지 않아도 되는 편리함 뒤에는, 코드만 봐서는 정확히 뭘 감시하고 있는지 한눈에 드러나지 않아서 코드가 복잡해질수록 오히려 유지보수하기 불편해질 수 있다는 걸 설명으로 배우고, 실습을 통해 확인했습니다.

## 3일차

### 📁 practices/component

### 1. LifecycleParent / LifecycleChild — 라이프사이클 훅

`<script setup>` 본문(생성) → `onMounted`(부착) → `onUpdated`(갱신) → `onUnmounted`(소멸)로 이어지는 흐름을 콘솔 로그로 추적했습니다. 자식 컴포넌트를 `v-if`로 껐다 켜는 버튼을 두고, `onMounted`에서 3초마다 도는 `setInterval` 타이머를 걸어둔 뒤 `onUnmounted`에서 `clearInterval`로 정리하도록 만들어서, 컴포넌트가 사라질 때 뒷정리를 해주지 않으면 어떤 일이 생기는지를 함께 확인했습니다.

**느낀점**:파괴 버튼을 눌렀는데도 타이머 로그가 계속 찍히는 걸 보고 onUnmounted에서 clearInterval을 해줘야 하는 이유를 알았습니다. 만드는 것보다 치우는 걸 신경 써야 했습니다.

### 2. PropsEmitsParent / PropsEmitsChild — Props & Emits

부모의 반응형 상태를 `:parent-data`로 자식에게 내려보내고, 자식은 `defineProps`로 받아 화면에 표시했습니다. 자식은 부모의 값을 직접 고치지 않고 `defineEmits(['update-request'])`로 등록한 커스텀 이벤트에 페이로드를 실어 올려보내고, 실제 상태 변경은 부모의 핸들러가 수행하도록 했습니다. (데이터는 아래로, 이벤트는 위로 — 단방향 데이터 흐름)

**느낀점**:처음엔 자식이 부모 값을 직접 바꾸면 될 텐데 왜 굳이 이벤트를 올려보내나 싶었는데, 값을 바꾸는 코드가 부모 한 곳에만 있으니 "누가 이 값을 바꿨는지" 찾을 필요가 없다는 게 실습하면서 이해됐습니다.

### 3. SlotDefaultParent / SlotDefaultChild — 기본 슬롯(Default Slot)

자식은 카드 테두리·여백 같은 껍데기만 갖고 내용 자리는 `<slot>`으로 비워둔 뒤, 같은 자식 컴포넌트에 문장 한 줄 / 제목+버튼 / 아무것도 안 주입 세 가지를 각각 넣어봤습니다. 아무것도 주입하지 않으면 `<slot>` 안에 적어둔 기본 콘텐츠(fallback)가 대신 렌더링되는 것도 확인했습니다.

**느낀점**:props로 내용을 넘기는 것과 뭐가 다른가 했는데, 같은 자식 컴포넌트에 문장 하나 / 제목+버튼 / 아무것도 안 넣기 세 가지를 넣어보니 차이가 보였습니다. props는 값을 넘기는 것이고 슬롯은 화면 조각을 통째로 넘기는 것이었습니다. 아무것도 안 넣었을 때 <slot> 안에 적어둔 기본 내용이 대신 나오는 것도, 빈 화면을 방지하는 장치라 실무에서 쓸모 있겠다 싶었습니다.

### 4. SlotNamedParent / SlotNamedChild — 이름 있는 슬롯(Named Slot)

자식이 `<slot name="header">`와 이름 없는 `<slot>` 두 자리를 열어두고, 부모가 `<template v-slot:header>`로 제목만 따로 지정해 넣었습니다. 슬롯이 여러 개일 때 어느 내용이 어느 자리로 들어갈지 이름으로 구분한다는 것을 확인했습니다.

**느낀점**:슬롯이 두 개가 되니 어디에 넣을지 이름으로 정해줘야 했습니다. 제목·본문 자리가 정해진 카드 컴포넌트를 만들 때 필요하겠다 싶었습니다.

### 5. SlotScopedParent / SlotScopedChild — 범위 슬롯(Scoped Slot)

자식이 내부에서 관리하는 데이터(`message`, `userCount`)를 `<slot :text="message" :count="userCount">`처럼 슬롯 속성으로 올려보내고, 부모가 `v-slot="slotBag"`으로 받아서 원하는 마크업으로 그렸습니다. 기본 슬롯이 "내용을 부모가 정한다"였다면, 범위 슬롯은 거기에 더해 **자식이 가진 데이터를 부모가 꺼내 쓸 수 있게** 해준다는 점이 다릅니다.

**느낀점**:자식이 올려보낸 데이터를 부모가 받아 쓸 수 있다는 게 차이였습니다. 과제 3에서 카드 상세 영역을 이 방식으로 만들었습니다

### 1. AxiosWeather — axios로 외부 API 호출하기

OpenWeatherMap에서 실시간 날씨를 받아오는 실습입니다. 버튼을 누르면 `isLoading`이 켜지면서 버튼이 비활성화되고, 응답이 오면 위치·기온·날씨 상태·습도를 카드로 보여줍니다. `try / catch / finally` 구조로 짰는데, 통신 실패는 `catch`에서 잡고 로딩 표시는 성공·실패와 무관하게 꺼져야 하므로 `finally`에 뒀습니다.

`fetch`와 비교되는 지점이 두 군데 있었습니다. 응답을 `res.json()`으로 한 번 더 변환할 필요 없이 `response.data`에 객체가 바로 들어오고, 4xx·5xx 응답이 오면 알아서 예외를 던져 `catch`로 넘어갑니다. (`fetch`는 404가 나도 요청 자체는 성공했다고 보고 `resolve`되기 때문에 `res.ok`를 직접 확인해야 합니다)

- 키를 코드에 직접 적지 않고 `.env`의 `VITE_OPENWEATHER_KEY`로 분리했습니다. 저장소가 공개라 소스에 박아두면 그대로 노출되고, 과정 요구사항에도 "키는 환경 변수로 조정하고 저장소에 업로드되지 않도록 한다"고 되어 있습니다.
- 좌표는 수업 예제(광주 인근) 대신 판교(`37.3948`, `127.1112`)로 바꿨습니다. `q=Pangyo`는 등록된 도시명이 아니라 조회되지 않고, 좌표나 `q=Seongnam`을 써야 `Seongnam-si`로 나옵니다.
- `units=metric`을 빼면 기온이 켈빈(K)으로 옵니다.

느낀점: 처음 눌렀을 때 401이 떠서 코드를 한참 들여다봤는데, 터미널에서 curl로 같은 주소를 직접 때려봐도 똑같이 401이 나왔습니다. 그제서야 코드 문제가 아니라 발급받은 키가 아직 활성화되기 전이라는 걸 알았습니다. 프론트엔드만 보고 있으면 통신이 안 될 때 원인이 내 코드인지 서버인지 구분이 안 되는데, 브라우저 밖에서 한 번 찔러보면 그 경계가 바로 갈린다는 걸 배웠습니다. 두 시간쯤 뒤에 다시 눌러보니 그대로 데이터가 들어왔습니다.

### 2. AxiosJson — axios로 CRUD 해보기

JSONPlaceholder(무료 가상 REST 서버)로 조회·등록·수정·삭제를 한 번씩 해봤습니다.

| 동작 | 메서드 | 호출 형태                                   |
| ---- | ------ | ------------------------------------------- |
| 조회 | GET    | `axios.get(URL, { params: { _limit: 3 } })` |
| 등록 | POST   | `axios.post(URL, payload)`                  |
| 수정 | PUT    | `axios.put(URL + '/' + id, payload)`        |
| 삭제 | DELETE | `axios.delete(URL + '/' + id)`              |

- 보낼 데이터를 두 번째 인자로 넘기면 `JSON.stringify` 없이 axios가 알아서 직렬화합니다.
- JSONPlaceholder는 요청을 받아주기만 하고 실제로 저장하지는 않습니다. 그래서 등록·수정·삭제 뒤에 화면을 갱신하려면 응답으로 받은 데이터를 `unshift` / 인덱스 교체 / `filter`로 직접 반영해야 했습니다.
- `onMounted`에서 GET을 호출해 화면이 열리자마자 목록이 채워지도록 했습니다.

느낀점: POST를 눌러도 새로고침하면 등록한 글이 사라져서 처음엔 실패한 줄 알았는데, JSONPlaceholder는 요청을 받아주기만 하고 실제로 저장은 안 하는 가상 서버였습니다. 그래서 등록·수정·삭제 뒤에 화면이 바뀌는 건 서버가 갱신해준 게 아니라 응답받은 데이터를 제가 배열에 직접 넣고 빼서 그렇게 보이는 것이었습니다. 서버 상태와 화면 상태가 별개고, 그 둘을 맞춰주는 게 프론트엔드 몫이라는 게 이 실습에서 제일 크게 남았습니다.

## 과제 2: Weather Composition 핸즈 온

지금까지 배운 반응형 상태(ref), computed, watch/watchEffect를 실제 데이터(날씨)에 적용해서, 도시를 검색·필터링하고 선택된 도시의 상태 변화를 감시하는 종합 실습을 진행했습니다.

실습 결과 보는법-> (`src/components/archive/WeatherComposition.vue`, 과제 4에서 라우터를 도입한 뒤로는 `/archive/composition` 주소에서 볼 수 있습니다.)

- 검색어(searchQuery), 선택된 도시 정보(selectedCityInfo), 도시별 날씨 데이터(weatherList)를 반응형 상태로 정의
- computed(filteredWeatherList)로 검색어가 도시 이름에 포함된 항목만 필터링해서 담아둠
- watch로 selectedCityInfo를 감시해 상태바 문구가 바뀔 때마다 콘솔로그를 남기고, watchEffect로는 감시 대상을 따로 지정하지 않고도 searchQuery 타이핑을 자동으로 추적
- 검색 결과 표시는 세 가지 경우(검색어 없음 / 일치하는 도시 있음 / 없음)를 모두 처리하되, 앞의 두 경우는 카드 마크업이 완전히 같아서 `v-if="sortedFilteredWeatherList.length > 0"` 하나로 합치고 "검색어와 일치함" 강조 표시만 검색어 유무로 켜고 끄도록 정리했습니다. (분기를 세 개로 벌리면 같은 카드 마크업이 두 벌 생겨서 한쪽만 고치는 실수가 나기 쉽다고 판단했습니다.)

### 개인별 Customization

과제 1과 마찬가지로 사용성을 기준으로 차별점을 잡되, 이번엔 반응형 상태·computed·watcher를 활용하는 실습 취지에 맞게 기능 쪽으로 더 풀어봤습니다.

- 기온순 정렬 토글: `sortOrder`(반응형 변수) + `sortedFilteredWeatherList`(computed로 필터링된 목록을 오름차순/내림차순/기본순으로 재정렬) + `watch(sortOrder, ...)`(정렬 기준이 바뀔 때마다 콘솔로그) 세트를 추가했습니다.
- 상세보기(체감 온도): 카드마다 "상세보기" 버튼을 두고, 누르면 온도와 날씨 상태를 조합해 computed로 계산한 체감 온도가 카드 안에 펼쳐지도록 만들었습니다. 검색어가 바뀌어서 상세보기를 열어둔 도시가 화면에서 사라지면, watch로 감지해서 상세보기 상태도 자동으로 닫히게 처리했습니다.
- 날씨 상태(맑음/비/구름/흐림)에 따라 카드 배경색과 테두리 색을 다르게 주고, 선택된 카드에는 파란 테두리 강조를, 검색어와 일치한 카드에는 초록 테두리 강조를 따로 표시해서 한눈에 구분되도록 했습니다.
- 검색어 유무에 따라 섹션 제목이 "지역별 날씨 현황" ↔ "검색 결과"로 자동으로 바뀌도록 했습니다.

**느낀점**: 과제 1에서는 디렉티브들을 조합하는 느낌이었다면, 이번엔 computed와 watch를 여러 겹으로 쌓아보는 경험이었습니다. filteredWeatherList 위에 sortedFilteredWeatherList를 얹고, 그 위에서 다시 체감 온도를 계산하는 식으로 computed끼리 연결되니까, "computed는 다른 computed에 의존할 수도 있다"는 게 실습으로 확 와닿았습니다. watch도 selectedCityInfo/sortOrder/expandedCityId 세 군데에 각각 다른 이유로 걸어보면서, watch를 무조건 많이 쓰는 게 아니라 "이 값이 바뀌는 걸 왜 감시해야 하는가"를 먼저 생각하고 붙여야 한다는 걸 느꼈습니다. 그리고 검색어가 바뀌었는데 상세보기 상태가 안 따라가는 엣지케이스를 직접 겪어보면서, watch가 단순히 로그를 남기는 용도만이 아니라 "다른 상태와 어긋나지 않게 맞춰주는" 용도로도 쓰인다는 걸 체감했습니다.

## 과제 3: Weather Component 핸즈 온

과제 2에서 한 파일에 몰려 있던 화면을 **기능 변경 없이** 여러 개의 Component 파일로 분리하는 실습을 진행했습니다. 부모는 상태를 갖고, 자식은 props로 받아 표시하고 emits로 사건만 알리는 단방향 데이터 흐름을 직접 만들어봤습니다.

실습 결과 보는법-> (`src/components/archive/WeatherParent.vue`, 과제 4에서 라우터를 도입한 뒤로는 `/archive/component` 주소에서 볼 수 있습니다.)

| 컴포넌트                | 역할                                                                                                            | props                                                | emits                         |
| ----------------------- | --------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ----------------------------- |
| `WeatherParent.vue`     | 모든 반응형 데이터(weatherList, searchQuery, selectedCityInfo, sortOrder, expandedCityId)와 computed/watch 보유 | -                                                    | -                             |
| `BaseDashboardCard.vue` | 검색박스·리스트박스의 공통 디자인(테두리/제목/여백), 내용은 `<slot>`으로 개방                                   | `title`                                              | -                             |
| `SearchBar.vue`         | 부모의 검색어를 전달받아 표시                                                                                   | `searchQuery`                                        | `update-query`                |
| `WeatherCard.vue`       | 선택된 도시 객체를 전달받아 표시                                                                                | `city`, `selected`, `query`, `expanded`, `feelsLike` | `select-card`, `click-detail` |
| `StatusBar.vue` (추가)  | 선택 도시 상태바 + 기온 정렬 토글                                                                               | `selectedCityInfo`, `sortOrder`                      | `toggle-sort`                 |

- 검색박스와 리스트박스의 공통 디자인을 `BaseDashboardCard`로 묶고, 도시 검색 / 날씨 현황은 `<slot>`으로 부모가 주입

- `WeatherCard`는 도시 객체를 props로 받아 표시하고, 카드 선택(`select-card`) / 상세보기(`click-detail`)를 부모에게 전달
- 각 컴포넌트에 해당하는 디자인은 `<style scoped>`로 각각 분리 (카드 색상 매핑처럼 스타일과 짝을 이루는 로직도 같이 이동)
- [참고] Slot으로 전달되는 자식(`SearchBar`, `WeatherCard`)은 시각적으로는 `BaseDashboardCard` 내부에 위치하지만 스크립트적으로는 부모 스코프에서 컴파일·평가되므로, `WeatherParent`에서 이 자식들과 직접 바인딩/통신이 가능했습니다.

### 개인별 Customization

과제 1·2에서는 "사용성"을 기준으로 잡았다면, 이번엔 실습 취지가 컴포넌트 분리인 만큼 **부모-자식 통신 방법을 props/emits 하나로만 끝내지 않는 것**을 기준으로 잡았습니다.

- **추가 컴포넌트(`StatusBar.vue`)**: 요구된 4개 외에, 부모에 남아 있던 "선택 도시 상태바 + 기온순 정렬 토글"(과제 2에서 직접 추가했던 기능) 영역을 하나 더 분리했습니다. 정렬 상태(`sortOrder`)는 부모가 계속 소유하고, 자식은 `toggle-sort` 이벤트만 올려보내도록 해서 상태의 주인이 흐려지지 않게 했습니다.
- **이름 있는 슬롯(named slot)**: `BaseDashboardCard`에 `#badge` 슬롯을 열어두고, 부모가 `"주" 검색 중` / `3곳` 같은 배지를 주입하도록 했습니다. 슬롯 내용이 부모 스코프에서 컴파일된다는 위 [참고] 내용을 코드로 직접 확인할 수 있는 부분입니다.
- **범위 슬롯(scoped slot)**: `WeatherCard`의 상세 영역을 `<slot name="detail" :city="city" :feels-like="feelsLike">`로 열어서, **틀은 자식이 갖고 내용은 부모가 정하도록** 했습니다. 부모는 이 자리에 과제 1 Mockup에서 만들었던 생활 팁(☂️/🧴/🧥)을 끼워 넣어서, 과제 1의 기능을 과제 3의 구조로 재사용했습니다. 부모가 아무것도 넘기지 않으면 자식이 가진 기본 내용(체감 온도)이 그대로 렌더링됩니다.
- **라이프사이클 훅 적용(`onMounted` / `onUnmounted`)**: 컴포넌트 단원에서 배운 라이프사이클을 과제 3에 적용했습니다. 이 화면은 `v-for` + 검색 필터라서, 검색어를 치는 순간 걸러진 카드가 실제로 언마운트됩니다. 콘솔을 열고 "주"를 입력하면 서울·수원·부산 등 8장에 `onUnmounted`가 찍히고, 전주·제주·광주 3장은 **`:key` 덕분에 재사용되어 아무 로그도 찍히지 않습니다.** 화면 로딩 시에는 카드 11장의 `onMounted`가 먼저 찍히고 그다음 부모(`WeatherParent`)의 `onMounted`가 찍혀서, 자식이 부모보다 먼저 마운트된다는 순서도 눈으로 확인할 수 있습니다.
- **props `validator` 적용**: 컴포넌트를 나누고 나면 "부모가 무엇을 넘겨야 하는가"가 곧 컴포넌트의 계약이 되므로, 그 계약을 props에 적어뒀습니다. `StatusBar`의 `sortOrder`는 `'none' | 'asc' | 'desc'` 셋 중 하나만, `WeatherCard`의 `city`는 `id`/`name`/`temp`/`status` 키를 모두 가진 객체만 받습니다. 실제로 `sortOrder`에 `'ASC'`를 넣어보니 `[Vue warn] Invalid prop: custom validator check failed for prop "sortOrder"` 경고가 떴습니다. validator가 없었다면 정렬이 조용히 기본 순서로 보이기만 하고 원인을 못 찾았을 것입니다.
- **검색어 하이라이트**: 부모에게 받은 검색어(`query`)를 자식이 직접 가공해서, 도시 이름 중 일치한 글자만 형광펜으로 강조했습니다. `v-html` 대신 문자열을 조각 배열로 쪼개 렌더링해서 XSS 여지를 남기지 않았습니다(기초 실습 `VueHtmlXss`에서 배운 내용 적용).
- **TransitionGroup**: 카드 목록을 `<TransitionGroup>`으로 감싸서, 정렬을 바꾸거나 검색으로 카드가 걸러질 때 위치 이동이 애니메이션으로 보이도록 했습니다. transition 클래스는 자식의 루트 엘리먼트에 붙는데 자식 루트에는 부모의 scoped 속성도 함께 붙기 때문에, 부모의 `<style scoped>`에서 제어가 가능했습니다.
- **날씨 상태 데이터 모델 정리(`weatherStatus.js`)**: 과제 2에서 `status: '맑음☀️'`처럼 값과 아이콘을 한 문자열에 붙여 저장하고 `status.includes('맑음')`으로 분기했는데, 컴포넌트를 나누면서 같은 문자열 검사를 카드·상태바·부모 세 군데에서 하게 되자 문제가 드러났습니다. 그래서 데이터는 `status: '맑음'` 값만 갖게 하고, 아이콘·카드 테마·체감온도 보정을 한 테이블(`weatherStatus.js`)에서 찾아 쓰도록 바꿨습니다. 분기가 문자열 검색에서 표 조회로 바뀌어서 `'맑음 가끔 비'` 같은 값이 두 조건에 동시에 걸리는 문제도 사라졌고, 과제 1의 아이콘 매핑도 같은 표를 쓰도록 통일했습니다.
- 과제 2의 `WeatherComposition.vue`는 분리 전 원본으로 그대로 남겨뒀습니다. 같은 화면을 "한 파일일 때"와 "컴포넌트로 나눴을 때"로 나란히 비교해볼 수 있게 하기 위함입니다.

**느낀점** : 과제 3을 하면서, 예전에 Squarespace로 사이트를 만들며 짜잘한 코드를 고쳤던 경험이 계속 떠올랐습니다. 그때 커스텀 CSS 패널에서 특정 블록만 손보려면 #block-yui*3_17*... 같은 알 수 없는 ID를 복사해 와야 했는데, 왜 이렇게 지저분하게 만들어놨을까 싶으면서도 그냥 그러려니 하고 썼습니다.
하지만 이번에 컴포넌트를 나누면서 각각에 <style scoped>를 붙여보니 그 이유를 알게 됐습니다. 빌드된 CSS를 열어보니 제가 쓴 .weather-card가 .weather-card[data-v-988ab3d4]로 바뀌어 있었고, 과제 2의 같은 이름 클래스에는 다른 해시(be093137)가 붙어 있었습니다. 클래스 이름이 같아도 스타일이 서로 안 새는 게 이것 때문이었습니다. Squarespace가 블록마다 고유 ID를 붙여둔 것도 결국 같은 문제를 푸는 방식이었습니다. 그때는 도구가 불편하게 만들어놓은 제약이라고 생각했는데, 직접 만들어보니 제약이 아니라 설계였다는걸 배웠습니다.

## 과제 4: Weather Router 핸즈 온

화면을 주소로 나누는 실습입니다. 과제 3까지는 한 화면 안에서 탭으로 전환했지만, 이번에는 Vue Router로 주소마다 다른 화면(view)을 띄우고, 상세보기를 별도 페이지로 분리했습니다.

- **라우터 설정 (`src/router/index.js`)**: 첫 화면(`WeatherHomeView`)만 정적 import로 두고 나머지는 `() => import(...)` 형태의 **Lazy Loading**으로 등록했습니다. Catch-all Route(`/:pathMatch(.*)*`)로 정의되지 않은 주소를 모두 받아 404 화면으로 보냅니다.
- **App.vue**: 화면을 직접 그리지 않고 내비게이션 바(`<RouterLink>`)와 메인 콘텐츠 영역(`<RouterView />`)만 배치합니다. 히어로 제목은 각 라우트의 `meta`에서 읽어오므로 화면마다 셸을 다시 짤 필요가 없습니다.
- **WeatherHomeView.vue**: 과제 3의 `WeatherParent`를 라우터 구조에 맞게 옮긴 메인 대시보드입니다. 상세보기 버튼을 누르면 카드 안에서 펼치는 대신 **Programmatic Navigation**(`router.push('/weather/' + id)`)으로 상세 페이지로 이동합니다. 자식(`WeatherCard`)은 여전히 `click-detail` 이벤트만 올려보내고, 이동 결정은 화면이 합니다.
- **WeatherDetailView.vue**: `/weather/:cityId` **동적 경로 매칭**으로 받은 도시 코드를 `props: true`로 전달받고, **Mount 시점(`onMounted`)에 Mock Data에서 도시 객체를 선택**합니다. 습도·풍속·강수확률·미세먼지·체감온도·최저/최고를 표시하며, 없는 도시 코드로 들어오면 안내 화면을 보여줍니다.
- **WeatherAboutView.vue**: 서비스 소개와 화면 구성표, 메인 대시보드로 돌아가는 버튼.
- **NotFoundView.vue**: Catch-all이 잡아낸 주소를 `route.fullPath`로 보여주는 404 화면.
- **Mock Data 공용화 (`src/data/weatherData.js`)**: 대시보드와 상세 페이지가 같은 도시 데이터를 봐야 하므로 배열을 한 곳으로 모으고, `findCityById` / `fineDustGrade` 같은 조회 함수를 함께 두었습니다. 과제 6에서 실제 API를 붙일 때 이 파일의 반환값만 교체하면 됩니다.

### 개인별 Customization

- **추가 view — 기온 통계 (`/stats`)**: 요구된 view 외에 하나를 더 만들었습니다. 새 데이터를 만들지 않고 대시보드와 같은 Mock Data를 `computed`로 집계해서, 최고·최저·평균·기온차와 날씨 상태별 도시 수를 막대로 보여줍니다. 최고/최저가 동점인 경우(전주·제주 22°)가 있어서 `filter`로 여러 도시를 함께 표시하도록 했고, 순위 목록의 도시 이름은 `<RouterLink>`로 상세 페이지에 바로 연결했습니다.
- **추가 view — 지난 실습 보관함 (`/archive/:step`)**: 라우터를 도입하면 과제 1~3과 기초 실습이 갈 곳을 잃기 때문에, 두 번째 동적 경로를 만들어 회차별로 보관했습니다. `:step` 값에 따라 `<component :is>`로 해당 회차를 갈아 끼웁니다. 이 화면은 기초 실습 30여 개를 품고 있어서 **Lazy Loading의 효과가 가장 잘 드러나는 라우트**이기도 합니다 — 빌드 결과 `ArchiveView` 청크가 42.5 kB로 따로 떨어져 나가면서 첫 화면 번들이 159 kB → 113 kB로 줄었습니다.
- **도시 목록 순서**: 기존에는 데이터를 넣은 순서 그대로였는데, 실제 기상 예보에서 지역을 읽는 순서(**수도권 → 충청 → 호남 → 영남 → 제주**)를 참고해 `서울 · 인천 · 수원 · 대전 · 세종 · 광주 · 전주 · 부산 · 대구 · 울산 · 제주`로 바꿨습니다. 지리적으로 이어져 있어서 목록을 훑을 때 눈이 따라가기 쉽고, 덕분에 정렬 토글의 "기본 순서"에도 "예보에서 읽는 지역 순서"라는 의미가 생겼습니다. 배열 순서와 어긋나지 않도록 `city_01`~`city_11` 번호도 다시 매겼습니다.
- **전역 네비게이션 가드**: `router.beforeEach`에서 라우트 `meta.title`로 브라우저 탭 제목을 바꾸고 이동 경로를 콘솔에 남깁니다. 화면이 여러 개가 되니 탭 제목이 전부 같으면 어느 페이지인지 구분이 안 돼서 넣었습니다.
- **scrollBehavior**: 페이지를 옮기면 맨 위로 스크롤하되, 뒤로가기(`savedPosition`)일 때는 보던 위치를 복원하도록 했습니다.
- **메인 화면 배치 재조정**: 과제 3에서는 검색·상태바·목록을 카드 세 개로 나눴는데, 앱 셸(헤더·히어로)이 생긴 뒤로는 구획이 한 겹 더 있는 셈이라 히어로 아래에 같은 무게의 흰 카드가 연달아 쌓여 리듬이 없었습니다. 그래서 **검색 + 정렬을 한 줄 툴바로 합쳐 카드를 두 개로 줄이고**, 선택한 도시 요약은 별도 카드 대신 목록 머리에 한 줄로 붙였습니다. 카드 그리드도 `flex wrap`에서 `grid auto-fill`로 바꿔서 마지막 줄 카드 폭이 균일해지도록 했습니다. 요구사항 3번이 "WeatherParent를 **참고하여** 경로에 맞게 작성"이므로, 기능(검색·정렬·선택·상세 이동)과 컴포넌트 구조는 유지하고 배치만 다시 잡았습니다.
- **`detailLabel` prop 추가**: 같은 `WeatherCard`인데 과제 3에서는 버튼이 카드 안을 펼치고(`상세보기 ▼`), 과제 4에서는 다른 페이지로 이동합니다(`상세보기 →`). ▼는 펼침을 뜻하는 신호라 이동 동작과 어긋나므로, 부모가 문구를 정할 수 있도록 선택적 prop을 열었습니다. 기본값이 빈 문자열이라 이 prop을 넘기지 않는 과제 3 화면의 출력은 그대로입니다.
- **과제 3의 `WeatherParent.vue`는 그대로 보존했습니다.** 과제 2→3 때와 같은 방식으로, 분리 전 결과물을 남겨 두고 `WeatherHomeView.vue`를 새로 만들었습니다.

### 궁금해서 해본 것 — 동적 경로 vs 쿼리스트링

수업 중에 교수님이 "예전 방식인 쿼리스트링이 더 편하다"고 하신 게 어떤 뜻인지 궁금해서, 같은 상세 화면을 두 방식으로 열어보고 비교했습니다.

```js
// 요구사항대로: 동적 경로 매칭
{ path: '/weather/:cityId', component: WeatherDetailView, props: true }

// 비교용: 쿼리스트링
{ path: '/weather', component: WeatherDetailView,
  props: (route) => ({ cityId: route.query.cityId ?? '' }) }
```

여기서 먼저 배운 것은 **`props`에 함수를 줄 수 있다**는 점입니다. 라우터가 쿼리를 prop으로 바꿔서 넘겨주기 때문에, `WeatherDetailView`는 자기가 경로로 받았는지 쿼리로 받았는지 몰라도 됩니다. 컴포넌트를 한 줄도 고치지 않고 두 방식을 모두 지원할 수 있었습니다.

`/weather/city_06`과 `/weather?cityId=city_06`은 개발 서버에서 똑같이 동작합니다. 그래서 **빌드한 결과물을 폴백 설정이 없는 정적 서버(`python3 -m http.server`)에 올려서** 실제 배포 환경을 흉내 내봤습니다.

| 주소                      | 결과       |
| ------------------------- | ---------- |
| `/`                       | ✅ 200     |
| `/weather/city_01`        | ❌ **404** |
| `/weather?cityId=city_01` | ❌ **404** |
| `/?cityId=city_01`        | ✅ 200     |
| `/stats`                  | ❌ **404** |

SPA는 `index.html` 하나뿐인데 브라우저가 새로고침 시 `/weather/city_01`을 서버에 그대로 요청하고, 서버에는 그런 파일이 없으니 404가 납니다. 개발 중에 이 문제가 안 보였던 건 Vite 개발 서버가 "어떤 경로로 와도 index.html을 준다"는 폴백을 대신 해주고 있었기 때문입니다.

여기서 예상과 달랐던 부분이 있습니다. **쿼리스트링으로 바꿔도 `/weather?cityId=...`는 똑같이 404였습니다.** 브라우저가 서버에 요청할 때 `?` 뒤는 경로가 아니라서, 서버가 보는 것은 여전히 `/weather`이기 때문입니다. 반면 `/?cityId=...`는 경로가 `/`라서 200입니다.

즉 **쿼리스트링이라서 편한 게 아니라, "경로가 항상 `/`"라서 편한 것**이었습니다. 예전 방식이 편하다는 말은 "모든 화면을 `/` 하나에 두고 파라미터로만 구분하면 서버 설정이 아예 필요 없다"는 뜻으로 이해했습니다.

정리하면 이렇습니다.

|                         | 동적 경로 `/weather/:cityId` | 쿼리스트링 `/?cityId=` |
| ----------------------- | ---------------------------- | ---------------------- |
| 서버 폴백 설정          | 필요                         | 불필요                 |
| URL이 자원을 표현       | 명확함                       | 약함                   |
| 선택적 파라미터 여러 개 | 조합이 늘면 불리             | 유리(순서·유무 자유)   |
| 경로별 방문 통계        | 쉬움                         | 어려움                 |

그래서 실무에서는 **무엇을 보는지는 경로로, 어떻게 보는지는 쿼리로** 나눈다는 것도 알게 됐습니다(`/weather/city_01?tab=hourly&unit=f`). 과제 4는 동적 경로 매칭이 요구사항이므로 그쪽을 기본으로 두고, 쿼리 방식은 비교용으로 함께 남겨뒀습니다. 배포 단계에서는 폴백 설정을 해줘야 한다는 것을 미리 확인한 셈입니다.

**느낀점**: 사이트를 만들어본 경험이 있어서 페이지마다 주소가 따로 있는 건 익숙했는데, SPA는 그걸 반대로 한다는 게 이번에 와닿았습니다. 파일은 index.html 하나뿐인데 주소만 여러 개인 척하는 구조라, 지금까지 당연하게 여겼던 "주소 = 파일"이 성립하지 않았습니다.

그 대가를 배포 실험에서 확인했습니다. 개발 서버에서는 /weather/city_01에서 새로고침해도 멀쩡해서 문제를 못 느꼈는데, 빌드한 결과물을 폴백 설정 없는 정적 서버에 올리니 404가 났습니다. 브라우저는 그 주소를 서버에 그대로 요청하고 서버엔 그런 파일이 없으니 당연한 결과인데, 개발 서버가 그 뒤처리를 대신 해주고 있어서 안 보였던 것이었습니다. 빌더로 사이트를 만들 때는 호스팅이 알아서 처리해주던 영역이라 신경 쓸 일이 없었는데, 직접 만들면 이건 내가 설정해야 하는 부분이라는 걸 알게 됐습니다.

교수님이 쿼리스트링이 편하다고 하신 이유도 이거겠다 싶어서 /weather?cityId=로 바꿔봤는데 이것도 똑같이 404가 났습니다. 서버 입장에선 ? 뒤가 안 보이니 결국 /weather를 찾는 건 마찬가지였습니다. 쿼리를 쓰느냐가 아니라 경로가 / 하나로 끝나느냐가 기준이었고, 예전 방식이 편하다는 말은 "화면을 전부 /에 두고 파라미터로만 구분하면 서버 설정이 필요 없다"는 뜻으로 이해했습니다.

지연 로딩은 효과가 숫자로 나와서 판단하기 쉬웠습니다. 기초 실습이 들어 있는 보관함 화면을 () => import(...)로 바꾸니 첫 화면 번들이 159kB에서 113kB로 줄고 보관함은 42.5kB짜리로 분리됐습니다. 어느 라우트를 지연 로딩할지는 감이 아니라 이 수치를 보고 정하면 되겠다 싶었습니다.

라우트를 짜는 일이 사실상 사이트맵을 짜는 일이라는 것도 이번에 느꼈습니다. 탭이 없어지면서 과제 1~3이 갈 곳이 없어져 /archive/:step을 따로 만들어야 했고, 상세 페이지를 다녀오면 정렬 상태가 초기화되는 것도 이때 드러났습니다. 컴포넌트와 상태의 수명이 같다는 뜻이었고, 화면 밖에서 살아남아야 하는 값은 따로 둬야 한다는 게 다음 과제로 이어졌습니다.

## 과제 5: Weather Store 핸즈 온

날씨 단위(섭씨/화씨) 설정을 Pinia 스토어로 관리하고, 여러 화면에 동시에 반영하는 실습입니다. 과제 4에서 화면을 주소로 나눠놨기 때문에, 헤더에서 바꾼 값이 메인·상세·통계까지 닿아야 합니다. props로 내려보내려면 중간 컴포넌트를 전부 거쳐야 해서 스토어가 필요한 상황이 자연스럽게 만들어졌습니다.

**과제 5는 과제 4 화면 위에 얹었습니다.** 과제 1~3처럼 별도 사본을 만들지 않은 이유는, 요구사항 자체가 "메인과 상세 날씨에 단위 설정 변경 적용"이라 기존 화면을 고치는 성격이기 때문입니다. (라우터는 앱에 하나뿐이라 사본을 만들 수도 없습니다)

- **`stores/configStore.js`**

  | 구분    | 이름         | 설명                                      |
  | ------- | ------------ | ----------------------------------------- |
  | state   | `unit`       | 단위를 저장하는 변수 (초기값 `'celsius'`) |
  | getters | `unitSymbol` | 현재 단위에 맞는 기호 (`℃` / `℉`)         |
  | actions | `toggleUnit` | `'celsius'` ↔ `'fahrenheit'` 토글         |

- **`UnitToggler.vue`**: 현재 단위를 표시하고 바꾸는 버튼. 이 컴포넌트는 **props를 하나도 받지 않습니다.** 단위는 부모가 아니라 스토어가 갖고 있기 때문입니다.
- **Navigation Bar 옆 배치**: 과제 4에서 `AppShell`에 열어뒀던 `#actions` 슬롯에 그대로 꽂았습니다. 셸을 고칠 필요가 없었습니다.
- **메인·상세·통계에 적용**: 원본 데이터는 항상 섭씨 숫자이고, 화면에 보일 때만 변환합니다.

### 개인별 Customization

- **변환식을 스토어 getter로 올림**: 슬라이드에서 `displayTemp` computed를 화면마다 두면 코드가 중복된다고 짚어주셨는데(참고: Composable로 해결 가능, 범위 제외), **getter가 함수를 반환하도록** 만들어서 풀었습니다. `displayTemp(28)`처럼 인자를 받아 계산하므로 메인·상세·통계가 같은 식을 공유합니다.
- **`displayDiff` getter 추가 — 기온 "차이"는 변환식이 다릅니다.** 통계 화면의 "기온 차" 항목에 `displayTemp`를 쓰면 9℃ 차이가 48℉ 차이로 나옵니다. 차이에는 `+32`를 더하면 안 되기 때문입니다(9 × 9/5 = 16℉ 차이가 정답). 온도와 온도차가 다른 값이라는 걸 이때 알았습니다.
- **추가 스토어 `dashboardStore`**: 정렬 기준(`sortOrder`)과 선택한 도시(`selectedCityId`)를 담습니다. 원래 `WeatherHomeView`의 로컬 `ref`였는데, 상세 페이지에 갔다 돌아오면 컴포넌트가 새로 만들어져서 정렬과 선택이 초기화됐습니다. 스토어로 옮기니 화면을 옮겨 다녀도 유지됩니다. 선택한 도시는 **객체가 아니라 id만** 저장하는데, 객체를 통째로 넣어두면 원본 데이터가 바뀌었을 때 옛 정보가 남기 때문입니다.
- **과제 3 화면은 섭씨 그대로입니다**: `WeatherCard`는 과제 3과 과제 5가 함께 쓰는 부품이라, `displayTemp` / `unitSymbol`을 **선택적 prop**으로 열었습니다. 넘기지 않으면 원본 값과 `°`를 그대로 쓰므로 `/archive/component`의 과제 3 화면은 예전과 똑같이 동작합니다.
- **새로고침하면 단위가 섭씨로 돌아갑니다.** `localStorage`에 저장하면 유지되지만 일부러 넣지 않았습니다. 스토어 상태가 메모리에 있다가 새로고침하면 사라진다는 것을 그대로 두는 편이 이번 실습의 학습 내용에 맞다고 판단했습니다.

**느낀점**:과제 3에서 상태는 부모가 갖고 자식은 받아 쓴다는 걸 배웠는데, 이번엔 그 규칙이 안 통하는 관계가 나왔습니다. 단위 토글은 헤더에 있고 그 값을 써야 하는 건 대시보드·상세·통계인데, 이 셋은 헤더의 자식이 아니라 라우터가 갈아 끼우는 화면들이라 props로 내려보낼 길이 없었습니다. 스토어가 그 규칙을 깨는 게 아니라 부모를 앱 전체로 한 칸 올린 거라고 생각하니 이해가 됐습니다.

그렇다고 다 스토어에 넣을 건 아니어서 기준을 정해야 했습니다. 검색어는 그 화면에서만 쓰고 나가면 없어져도 되는 값이라 그대로 뒀고, 정렬 기준이랑 선택한 도시는 상세 페이지 갔다 오면 초기화되는 게 걸려서 스토어로 옮겼습니다. 화면 안에서만 사는 값이냐 화면을 건너 살아남아야 하는 값이냐로 나누니 정리가 됐습니다.

제일 손이 많이 간 건 단위 변환이었습니다. 화면마다 변환식을 쓰면 똑같은 코드가 세 군데 생겨서 getter가 함수를 돌려주게 만들어 한 곳에서 처리했는데, 그러고 나서 통계 화면의 "기온 차"가 이상하게 나오는 걸 발견했습니다. 9℃ 차이가 48℉로 찍혀 있었는데, 온도 변환식을 차이에 그대로 쓴 게 문제였습니다. 온도랑 온도차는 생긴 건 같은데 다른 값이라 +32를 빼야 했고, 결국 displayDiff를 따로 만들었습니다. 단위를 바꾼다는 게 숫자에 식 하나 씌우는 일인 줄 알았는데 값의 성격부터 봐야 하는 일이었습니다.

새로고침하면 단위가 섭씨로 돌아가는 것도 그대로 뒀습니다. localStorage에 넣으면 유지되지만, 스토어에 있는 값은 메모리에 있다가 새로고침하면 사라진다는 걸 눈으로 봐두는 게 이번엔 더 맞다고 봤습니다.

## 과제 6: Weather Axios 핸즈 온

Mock Data를 걷어내고 실제 날씨 API를 붙이는 실습입니다. 과제 1~5까지 만든 화면 구조는 그대로 두고, 값의 출처만 바꾸는 것이 목표였습니다.

### 요구사항 1 — 실제 날씨 데이터 적용

- **`src/api/weatherApi.js`**: OpenWeatherMap 호출을 한 곳에 모았습니다. 화면(view)은 axios를 직접 부르지 않고 이 파일의 함수만 씁니다. `axios.create()`로 인스턴스를 만들어 `baseURL`·API 키·`units=metric`·`lang=kr`을 미리 박아두면, 호출할 때마다 같은 값을 반복해서 적지 않아도 됩니다.
- **응답을 그대로 쓰지 않고 우리 형태로 바꿉니다.** 화면이 `data.main.temp` 같은 OpenWeatherMap의 구조를 직접 알게 되면, 나중에 API를 바꿀 때 모든 화면을 고쳐야 합니다. 그래서 이 파일에서 한 번 변환한 뒤 넘깁니다.
- **상태 매핑**: OpenWeatherMap의 `weather[0].main`(`Clear`/`Rain`/`Clouds`…)을 과제 3에서 만든 한글 상태(`맑음`/`비`/`구름`/`흐림`)로 옮겼습니다. 덕분에 `weatherStatus.js`의 아이콘·카드 색·테마를 하나도 고치지 않고 그대로 썼습니다. 구름은 양에 따라 느낌이 달라서 `id`가 803·804(broken/overcast)면 `흐림`으로 따로 나눴습니다.
- **`src/stores/weatherStore.js`**: 받아온 날씨를 스토어에 두고 대시보드·상세·통계가 함께 봅니다. 화면마다 각자 호출하면 이동할 때마다 API를 다시 부르게 됩니다.
- **`Promise.all`로 11개 도시를 동시에** 부릅니다. 하나씩 `await`하면 도시 수만큼 기다려야 합니다.
- **로딩·에러 상태**: 통신은 실패할 수 있으므로 로딩 문구, 에러 문구, 다시 시도 버튼을 넣었습니다. 401이면 "키가 올바르지 않거나 아직 활성화되지 않았습니다"로 원인을 좁혀 보여줍니다.
- **체감 온도는 더 이상 직접 계산하지 않습니다.** 과제 2~5에서는 날씨 상태에 따라 임의로 ±보정했는데, 이제 API가 주는 `feels_like`를 씁니다.

### 요구사항 2 — OpenWeatherMap API 추가

| API                     | 쓰는 곳                                                                          |
| ----------------------- | -------------------------------------------------------------------------------- |
| Air Pollution           | 상세 페이지의 미세먼지(PM10)·초미세먼지(PM2.5). Mock 값이던 자리를 실측치로 교체 |
| 5 Day / 3 Hour Forecast | 상세 페이지 "앞으로 24시간" — 3시간 간격 8칸, 기온과 강수확률(`pop`)             |
| Weather Map Tiles       | 지도 위에 겹치는 기온·구름·강수 레이어                                           |

대기오염과 예보는 서로 다른 엔드포인트라 `Promise.all`로 동시에 호출합니다. 하나씩 기다리면 두 배로 기다리게 됩니다.

### 요구사항 3 — 기타 외부 API

| API / 기능                                         | 쓰는 곳                                                    |
| -------------------------------------------------- | ---------------------------------------------------------- |
| **OpenStreetMap Nominatim** (지오코딩)             | 도시 이름 → 좌표 (도시 추가), 좌표 → 도시 이름 (현재 위치) |
| **브라우저 Geolocation API**                       | 접속한 사람의 현재 위치 좌표                               |
| **Leaflet** (지도 라이브러리) + OpenStreetMap 타일 | 상세 페이지의 지도                                         |

**두 서비스가 이어져서 하나의 기능이 됩니다.** Nominatim이 이름을 좌표로 바꿔주고, 그 좌표를 OpenWeatherMap에 넘겨 날씨를 받습니다. 현재 위치는 그 반대 방향으로, 브라우저가 준 좌표를 Nominatim이 지명으로 바꾸고 다시 OpenWeatherMap이 날씨를 채웁니다.

### 개인별 Customization

- **API 키는 `.env`로 분리했습니다.** 수업 예제는 키를 소스에 직접 적었지만, 저장소가 공개라 그대로 올리면 노출됩니다. `.env`는 `.gitignore`에 넣고 `.env.example`만 올렸습니다. 다만 Vite의 `VITE_` 변수는 빌드 결과물에 포함되므로 배포하면 브라우저에서 볼 수 있다는 한계도 함께 알게 됐습니다.
- **검색 결과의 품질 문제를 두 번 고쳤습니다.** Nominatim에 "속초"를 그대로 던지면 힐스테이트 속초·속초 코다리냉면 같은 아파트와 식당이 15건 나오고 정작 속초시는 안 나옵니다. `class`가 `place`/`boundary`인 것만 남기고, 그래도 결과가 없으면 한글 지명에 `시`를 붙여 한 번 더 조회하도록 했습니다. 그리고 "구리"를 검색하니 러시아의 동명 지역이 먼저 잡혀서, 한글 검색일 때는 `countrycodes=kr`로 범위를 좁혔습니다. **응답이 오는 것과 쓸 만한 응답이 오는 것은 다른 문제**라는 걸 알게 된 부분입니다.
- **지도의 줌을 5로 고정하고 최대 8로 제한했습니다.** 처음에 줌 9로 만들었더니 날씨 레이어가 거의 안 보였습니다. 타일을 직접 받아 용량을 재보니 서울 기준 강수 타일이 줌 4에서 66KB인데 줌 9에서는 334바이트, 즉 사실상 빈 이미지였습니다. 날씨 타일은 넓은 지역의 분포를 보는 용도라, 도시를 확대해서 보는 지도로 만들면 아무것도 안 보이는 게 당연했습니다.
- **레이어 기본값은 기온입니다.** 강수만 있으면 비가 안 오는 날 빈 지도가 됩니다. 기온 레이어는 항상 색이 칠해져 있어서 화면이 비지 않습니다.
- **Leaflet은 동적 import로 불러옵니다.** 라이브러리가 150KB라 첫 화면 번들에 넣으면 대시보드까지 무거워집니다. 상세 페이지에 들어갈 때만 내려받도록 `defineAsyncComponent`를 썼습니다. 과제 4의 라우트 지연 로딩을 컴포넌트 단위로 적용한 것입니다.
- **지도는 `onUnmounted`에서 직접 치웁니다.** Leaflet은 Vue 밖에서 DOM을 직접 다루는 라이브러리라, 컴포넌트가 사라져도 지도 인스턴스와 이벤트 리스너가 남습니다. 3일차 라이프사이클 실습의 `clearInterval`과 같은 상황입니다.
- **히어로에 현재 위치 날씨를 띄웁니다.** 브라우저 Geolocation으로 좌표를 받고, Nominatim으로 지명을 붙이고, OpenWeatherMap으로 날씨를 채웁니다. 히어로 배경도 예전에는 6·9·17·20시로 제가 임의로 나눴는데, 이제 그 지점의 **실제 일출·일몰 시각**을 기준으로 낮과 밤을 가릅니다. 위치 권한을 거절하면 경고 없이 선택한 도시(또는 목록 첫 도시)로 돌아갑니다.
- **대시보드를 카드 하나로 합쳤습니다.** 검색 카드 / 도시 추가 카드 / 목록 카드 세 개가 똑같이 생겨서 무엇이 무엇인지 구분되지 않았습니다. 검색·정렬·도시 추가는 전부 "이 목록을 다루는 도구"라 목록과 같은 상자에 넣고, 각각의 사용 빈도에 따라 형태를 다르게 했습니다 — 검색은 입력창, 정렬은 헤더의 알약, 도시 추가는 눌러야 펼쳐지는 버튼.
- **추가한 도시는 `localStorage`에 저장합니다.** "이 도시를 보고 싶다"는 사용자의 선택이라 다음 방문에도 유효한 값이기 때문입니다. 반대로 정렬 기준·선택한 도시·날씨 데이터는 저장하지 않습니다. 이 저장 덕분에 `/weather/extra_...` 주소를 새로고침해도 좌표를 찾아 다시 호출할 수 있습니다.
- **추가할 수 있는 도시를 10곳으로 제한했습니다.** 처음에는 제한을 두지 않았는데, 화면을 열 때마다 기본 도시 + 추가 도시를 `Promise.all`로 **한꺼번에** 호출한다는 점이 걸렸습니다. OpenWeatherMap 무료 요금제가 분당 60회라, 도시가 50곳쯤 되면 새로고침 한 번으로 한도를 넘겨 429가 납니다. 10곳이면 한 번에 21회라 한도의 3분의 1 수준이고, 화면으로도 1280px 기준 6열 4행에 들어와서 스크롤 한 번이면 다 보입니다. 한도에 닿으면 검색 버튼을 비활성화하고 `추가한 도시 3/10곳`으로 남은 수를 보여주되, 스토어에서도 한 번 더 막았습니다. **화면에서 막는 것과 데이터에서 막는 것은 다른 일**이라, 버튼을 우회해도 목록이 늘어나지 않도록 두 곳에서 확인합니다.
- **통계는 국내 기본 도시만 집계합니다.** 검색으로 해외 도시를 추가할 수 있게 되면서, 남반구 도시를 넣으면 계절이 반대라 최저 기온이 항상 그 도시가 되고 평균도 뜻을 잃습니다. 제외한 개수와 이유를 화면에 함께 적어서, 숫자가 안 맞아 보이는 일이 없도록 했습니다.
- **과제 1~3 화면은 여전히 Mock으로 돌아갑니다.** `weatherStatus.js`의 `feelsAdjust`는 최신 화면에서는 쓰지 않지만, 과제 2·3이 체감온도를 직접 계산하는 것이 그날의 학습 내용이라 지우지 않고 남겨뒀습니다.

**느낀점**:이번 과제는 지금까지 제가 지어낸 숫자를 진짜로 바꾸는 일이었습니다. 그런데 시작부터 401이 떠서 환경변수를 잘못 읽나, 주소가 틀렸나 하고 코드만 한참 봤는데, 터미널에서 curl로 같은 주소를 때려봐도 똑같이 401이었습니다. 그제서야 발급받은 키가 아직 활성화 전이라는 걸 알았습니다. 브라우저 안에서만 보고 있으면 원인이 내 코드인지 저쪽 서버인지 구분이 안 되는데, 밖에서 한 번 찔러보면 바로 갈리더라고요.

대기오염 API를 붙인 건 상세 페이지 때문이었습니다. 과제 4에서 미세먼지 칸을 만들어뒀는데 그 숫자가 제가 적당히 넣은 값이었습니다. 정작 오늘 나갈지 말지 정할 때 제일 먼저 보는 게 그건데 가짜라 아무 소용이 없었습니다. 붙이고 나니 PM10, PM2.5가 실측으로 들어와서 그제야 그 칸이 제 역할을 하게 됐습니다.

도시 검색은 목록이 제가 고른 11개뿐이라는 게 걸려서 만들었습니다. 정작 자기가 사는 데가 없으면 쓸 이유가 없는 앱이니까요. 그런데 날씨를 부르려면 좌표가 필요해서 OpenStreetMap 지오코딩을 붙였는데, 여기서 응답이 오는 것과 쓸 만한 응답이 오는 게 다른 문제라는 걸 겪었습니다. "속초"를 치면 힐스테이트 속초, 속초 코다리냉면 같은 게 열다섯 건 나오고 정작 속초시는 없었습니다. 응답은 200이고 데이터도 멀쩡한데 원하는 건 하나도 없는 상황이라, 결과에서 도시·행정구역만 남기고 그래도 없으면 "시"를 붙여 다시 찾도록 손봤습니다. "구리"에 러시아 지역이 잡히던 것도 그때 같이 걸렀습니다.

지도는 숫자만 늘어놓으니 비가 어디쯤 오고 있는지가 안 보여서 넣었습니다. 처음엔 강수 레이어를 켜도 아무것도 안 나와서 타일 주소가 틀렸나 했는데, 타일을 직접 받아 용량을 재보니 줌 4에서 66KB인 게 줌 9에서는 334바이트, 사실상 빈 이미지였습니다. 데이터가 없는 게 아니라 제가 너무 당겨서 본 거였습니다. 날씨 타일은 넓은 지역을 보라고 만든 건데 도시 하나 확대하는 지도로 써놨으니 안 보이는 게 당연했습니다.

데이터가 진짜가 되니까 안 보이던 것도 드러났습니다. 시험 삼아 호주 도시를 추가했더니 계절이 반대라 최저 기온이 무조건 그 도시가 되고 평균은 아무 뜻 없는 숫자가 됐습니다. Mock으로 국내 11곳만 다룰 때는 "전부 같은 기준"이라는 걸 당연하게 깔고 있었던 겁니다. 그런데 정작 화면 자체는 거의 안 고쳤습니다. 과제 3에서 날씨 상태를 표로 정리해둔 덕분에 API가 주는 Clear, Clouds를 우리 상태로 옮기기만 하면 아이콘도 카드 색도 그대로 돌아갔고, 과제 5에서 스토어를 만들어둔 덕분에 받아온 값을 넣을 자리도 이미 있었습니다.

## 과제 7: Weather UI Library 핸즈 온

외부 UI 라이브러리(**Element Plus**)를 선정해 지금까지 만든 화면에 적용하는 실습입니다. 강의 자료의 알림 컴포넌트 슬라이드가 `ElMessage` · `ElMessageBox` · `ElNotification` 기준으로 쓰여 있어서 Element Plus를 골랐습니다.

과제 1~3 결과물(`components/archive/`)은 그대로 두고, 현재 살아 있는 화면(대시보드·상세·통계·404)에만 적용했습니다.

### 적용 기준 — 예쁘게 만드는 도구가 아니다

수업에서 **UI 라이브러리의 값어치는 입력 검증 같은 상호작용 품질에 있고, 카드를 예쁘게 만드는 데 쓰는 것이 아니다**라는 말씀이 있었습니다. 그 기준으로 적용 대상을 골랐습니다.

**가져다 쓴 것 — 직접 만들면 품질이 떨어지는 것**

| 자리                                                      | 이유                                                                                           |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `el-form` 입력 검증                                       | 언제 검사할지, 메시지를 어디에 띄울지, 통과 못 하면 제출을 어떻게 막을지를 전부 직접 짜야 한다 |
| `ElMessage` 토스트                                        | 위치·애니메이션·자동 닫힘·여러 개 쌓일 때 처리                                                 |
| `ElMessageBox` 확인창                                     | 포커스 가둠·ESC 처리·스크롤 잠금                                                               |
| `el-skeleton`                                             | 로딩 중 자리 잡기 (글자가 숫자로 바뀔 때 칸이 들썩이는 것 방지)                                |
| `el-empty` · `el-result` · `el-alert`                     | 빈 화면·404·에러의 아이콘과 여백 배치                                                          |
| `el-tag` · `el-radio-group` · `el-progress` · `el-switch` | 상태 표시와 선택 컨트롤                                                                        |

**그대로 둔 것** — 날씨 카드, 히어로, 앱 셸, 디자인 토큰. 이 앱에 맞춰 만든 것이라 라이브러리 컴포넌트로 바꾸면 지금까지 쌓은 디자인이 오히려 뭉개집니다.

### 개인별 Customization

- **주문형(on-demand) 로딩**: `app.use(ElementPlus)`로 통째로 등록하면 쓰지도 않는 컴포넌트와 CSS까지 번들에 들어갑니다. `unplugin-auto-import` + `unplugin-vue-components`로 **실제로 쓴 것만** import되도록 설정했습니다. 처음에는 "통째로 등록하면 400KB쯤 되겠지"라고 어림잡아 적어뒀는데, 확인해보니 짐작보다 훨씬 컸습니다. `main.js`를 `app.use(ElementPlus)` + 전체 CSS import로 잠깐 바꿔서 실제로 재봤습니다.

| 방식                                 | 첫 화면 JS + CSS |
| ------------------------------------ | ---------------- |
| 주문형 (지금)                        | **196 KB**       |
| `app.use(ElementPlus)` — 통째로 등록 | **1,436 KB**     |

**7.3배**입니다. 이 앱이 쓰는 Element Plus 컴포넌트는 열 개 남짓인데, 통째로 등록하면 안 쓰는 200개 넘는 컴포넌트와 그 CSS 전부가 첫 화면에 실립니다. 설정 두 줄로 갈리는 차이라, 어림짐작으로 적어두지 않고 재보길 잘했습니다.

- **테마를 우리 토큰에 맞춤**: Element Plus 기본 파랑(`#409EFF`)을 그대로 두면 파랑이 두 종류가 됩니다. `--el-color-primary` 같은 변수에 우리 `--sk-*` 토큰을 넘겨서 기존 화면과 섞이게 했습니다.
- **입력 검증 (`el-form`)**: 도시 추가 입력창에 네 가지 규칙을 걸었습니다 — 필수, 두 글자 이상, 30자 이하, 한글·영문만. 특히 마지막 규칙은 실용적인 이유가 있습니다. `123!!` 같은 값을 지오코딩에 보내면 응답은 200으로 오지만 쓸모없는 결과만 나옵니다. **애초에 보내지 않는 것이 맞습니다.** 검증을 통과해야만 요청이 나갑니다.
- **즐겨찾기 (`favoriteStore`)**: 과제 1에서 만들었던 별표를 되살렸습니다. 그때는 화면 안에서만 살아 있는 값이었지만, 이제 스토어와 `localStorage`가 있으니 화면을 옮기거나 새로고침해도 남습니다. 도시 객체가 아니라 **id만 저장**합니다 — 날씨는 매번 새로 받으므로 객체를 넣어두면 옛 기온이 남습니다. 목록에서 사라진 도시는 `prune()`으로 즐겨찾기에서도 정리합니다.
- **즐겨찾기는 필터가 아니라 묶음으로**: 처음에는 "즐겨찾기만 보기" 토글(`el-switch`)을 만들었는데, 사용자가 모드를 껐다 켜야 하고 즐겨찾기가 없을 때는 비활성 버튼만 자리를 차지했습니다. 목록 위쪽에 **따로 모아 보여주는 방식**으로 바꾸니 전환 없이 둘 다 보입니다.
- **데이터 신선도**: 헤더에 `방금 기준` / `n분 전 기준`을 표시하고 새로고침 버튼을 뒀습니다. 날씨는 시간이 지나면 낡는 값인데, 화면만 봐서는 방금 값인지 10분 전 값인지 알 수 없었습니다. `loadedAt`은 스토어에 이미 있었는데 화면에서 쓰지 않고 있었습니다.
- **검색 → 도시 추가 연결**: "속초"를 검색해서 결과가 없다는 것은 **목록에 없는 도시를 찾았다는 뜻**이고, 바로 추가할 타이밍입니다. 그런데 안내만 띄우고 끝나서 사용자가 위로 올라가 다시 검색해야 했습니다. 빈 화면에서 바로 이어지도록 했습니다.
- **기호 문자를 SVG 아이콘으로 (`@element-plus/icons-vue`)**: 별표·닫기·새로고침을 `★ ☆ ✕ ↻` 같은 글자로 찍고 있었습니다. 이 글자들은 **폰트에 그 글자가 들어 있어야만** 보이고, 없으면 네모(□)로 떨어집니다. 특히 `↻`는 기본 폰트에 빠져 있는 경우가 많아서, 제 맥에서만 멀쩡하고 채점 환경에서는 깨질 수 있는 상태였습니다. SVG 아이콘은 모양을 직접 갖고 다니므로 OS를 타지 않습니다. 아이콘에는 `aria-hidden`을 걸고 의미는 `aria-label`이 전달하도록 두었습니다. (날씨 이모지는 폰트 문제가 아니라 플랫폼별 그림 차이라 그대로 뒀습니다.)
- **카드 정보 밀도**: 카드에 도시·기온·상태 세 줄만 있으니 11장이 늘어섰을 때 같은 것의 반복으로만 읽혔습니다. **체감온도와 습도**를 덧붙였습니다 — 이미 받아둔 응답에 들어 있던 값이라 API 호출은 늘지 않습니다. 서울 기준 기온 30.8°에 체감 35.9°로 5도가 차이 나서 정보로서 값이 있습니다. 처음에는 최저/최고를 넣으려 했는데, 현재날씨 응답의 `temp_min`·`temp_max`는 **오늘의 최저/최고가 아니라 같은 시각 주변 관측소들 사이의 편차**였습니다(서울 실측 `temp 30.8 / min 30.8 / max 31.8`). 도시 한 곳만 보면 현재 기온과 거의 같아서 고장난 것처럼 보이므로 쓰지 않았습니다. 진짜 일교차는 예보 API가 필요한데 도시마다 호출이 한 번씩 더 붙어서, 상세 화면에만 남겨뒀습니다.
- **카드 클릭 반응**: 카드를 눌러도 아무 일도 없는 것처럼 느껴졌습니다. 선택 결과가 표시되는 요약줄이 카드보다 **위에** 있어서 눈에 안 들어왔기 때문입니다. 선택된 카드에 `선택됨` 글자를 넣고, 요약줄이 바뀔 때 잠깐 강조하도록 했습니다.

### 라이브러리가 대신 해주지 않는 것

UI 라이브러리를 붙이는 과정에서 오히려 **직접 판단해야 하는 문제**를 두 개 만났습니다.

- **막대 그래프가 데이터를 왜곡하고 있었습니다.** 통계의 기온 순위 막대를 `el-progress`로 바꿨는데, 길이 계산은 우리 코드였습니다. 그날의 최저~최고를 0~100%로 늘려 그리다 보니, 30~33℃로 좁게 몰린 날에는 **1℃ 차이가 막대의 33%**가 되어 최저 도시가 빈 막대로 보였습니다. 막대는 0에서 시작하는 그림이라 "몇 배 차이"로 읽히므로, 기준을 −10~40℃로 고정해서 3℃ 차이가 6%p로 보이게 고쳤습니다.
- **화면이 "없는 것"과 "아직 안 온 것"을 구분하지 못했습니다.** 상세 페이지에서 상세보기를 누르면 잠깐 "도시를 찾을 수 없습니다"가 떴습니다. 로딩 중 분기가 없어서 `city`가 채워지기 전까지 마지막 `v-else`가 표시된 것입니다. 로딩·성공·요청 실패·도시 없음 네 가지 상태를 나눠서 처리했습니다. 이 버그는 제가 검증할 때마다 몇 초 기다린 뒤에 확인해서 놓치고 있었습니다.

**느낀점**: 라이브러리를 붙이면 그만큼 품질이 올라갈 거라고 막연히 생각했는데, 대신 해주는 범위가 생각보다 좁았습니다. 제일 크게 걸린 건 통계 화면의 막대 그래프였습니다. `el-progress`로 바꾸고 나니 손으로 그렸을 때보다 훨씬 그럴듯해 보여서 다 됐다고 생각했는데, 며칠 뒤에 보니 기온이 30~33℃로 몰린 날에 최저 도시가 빈 막대로 나와 있었습니다. 컴포넌트는 시키는 대로 퍼센트를 그렸을 뿐이고, 그 퍼센트를 계산한 건 제 코드였습니다. 그날의 최저~최고를 0~100%로 늘려 쓰고 있어서 1℃ 차이가 막대의 33%가 되어 있었던 겁니다. 라이브러리가 보기 좋게 만들어준 덕에 오히려 틀린 걸 늦게 알아챈 셈이라, 겉모습이 완성돼 보이는 것과 값이 맞는 것은 별개라는 걸 확실히 배웠습니다.

디자인을 해봤던 입장에서 처음엔 카드나 헤더까지 라이브러리 걸로 바꾸고 싶었는데, 수업에서 UI 라이브러리의 값어치는 입력 검증 같은 상호작용 품질에 있다는 말씀을 듣고 기준을 바꿨습니다. 그러고 나서 보니 실제로 직접 만들면 어설퍼지는 것들이 따로 있었습니다. 확인창의 포커스 가둠이나 ESC 처리, 토스트가 여러 개 쌓일 때의 배치 같은 것은 만들 수는 있어도 제대로 만들기는 번거로운 일이었습니다. 반대로 날씨 카드는 이 앱에 맞춰 만든 것이라 바꿨으면 지금까지 쌓은 게 뭉개졌을 겁니다. 어디까지 가져다 쓰고 어디서 멈출지를 정하는 게 라이브러리를 붙이는 일의 절반이었습니다.

## 과제 8: Weather Deployment 핸즈 온

지금까지 만든 것을 **남에게 넘길 수 있는 상태**로 만드는 회차입니다. 코드 품질 도구로 훑고, 소스에 박혀 있던 설정값을 환경 변수로 빼고, 빌드해서 배포합니다.

### ESLint — 에러 8개가 있었습니다

`npm run lint`를 돌리자 `no-undef` 에러가 8개 나왔습니다. 전부 같은 원인이었습니다.

```
src/views/WeatherHomeView.vue
  51:23  error  'ElMessage' is not defined  no-undef
  ...
```

과제 7에서 Element Plus를 주문형으로 붙이면서 `unplugin-auto-import`가 `ElMessage`의 `import` 구문을 **빌드할 때 넣어주도록** 했습니다. 그래서 소스에는 `import`가 없습니다. 빌드는 멀쩡히 되지만, **ESLint는 빌드를 거치지 않고 소스만 읽으므로** 선언된 적 없는 변수로 봅니다.

빌드 산출물에는 실제로 들어오는 값이니 전역으로 인정해주는 것이 맞습니다.

```js
globals: {
  ...globals.browser,
  ElMessage: 'readonly',
  ElMessageBox: 'readonly',
},
```

`readonly`로 둔 이유가 있습니다. 우리가 저 이름에 값을 덮어쓰는 일은 정상적인 코드에서 일어나지 않으므로, 그때는 오히려 에러를 내는 편이 낫습니다.

플러그인이 globals 목록을 파일로 뽑아주는 옵션도 있지만, 그러면 **한 번 빌드해야 lint가 통과하는 상태**가 됩니다. 저장소를 새로 받은 사람이 `npm run lint`부터 돌리면 실패합니다. 지금 자동 임포트되는 것은 이 둘뿐이라 직접 적었습니다.

### ESLint Custom Rules

```js
{
  name: 'app/custom-rules',
  rules: {
    eqeqeq: ['error', 'always'],
    'no-console': 'off',
    'no-unused-vars': 'warn',
    'vue/multi-word-component-names': 'off',
  },
},
```

배열은 뒤에 올수록 앞 설정을 덮어쓰므로 `skipFormatting` 바로 앞에 뒀습니다.

- **`eqeqeq`** — 이 앱은 API가 준 숫자와 화면에서 만든 문자열이 섞이는 곳이라 실질적으로 필요합니다. `==`는 타입이 다르면 몰래 변환해서 비교하기 때문에 `'20' == 20`이 `true`가 됩니다.
- **`no-console: off`** — 이 저장소에서 `console.log`는 디버깅 찌꺼기가 아니라 **무엇이 언제 실행되는지 보여주는 장치**입니다. `watch`/`watchEffect`가 언제 도는지, 카드가 언제 생기고 사라지는지(`onMounted`/`onUnmounted`)를 콘솔에서 확인하는 것이 그날의 학습 내용이었습니다.
- **`no-unused-vars: warn`** — 안 쓰는 변수는 지우는 게 맞지만, 에러로 막으면 작업 중간에 저장을 못 합니다.

검출도 확인했습니다. 컴포넌트에 `if (userAge == 20)`을 일부러 넣자 바로 잡혔습니다.

```
47:13  error  Expected '===' and instead saw '=='  eqeqeq
```

**최종 결과: `npm run lint` — 0 errors, 0 warnings.**

### Prettier — 백틱은 바뀌지 않았습니다

슬라이드의 미션 코드를 그대로 넣고 `npm run format`을 돌렸습니다.

```js
// 전
const myRegion = `Suwon`
const regionGreeting = `웰컴투${myRegion}`

// 후
const myRegion = `Suwon`
const regionGreeting = `웰컴투${myRegion}`
```

공백과 세미콜론은 정리됐는데 **백틱은 그대로였습니다.** `singleQuote: true`가 걸려 있는데도 그렇습니다.

Prettier가 따옴표를 통일하는 것은 `'문자열'`과 `"문자열"` 사이의 이야기고, 백틱은 따옴표의 한 종류가 아니라 **템플릿 리터럴이라는 다른 문법**이기 때문입니다. 바꾸면 서식이 아니라 코드를 고치는 셈이 됩니다. 실제로 아랫줄의 백틱은 `${}` 때문에 필수라 바꾸면 동작이 깨집니다. 서식 도구가 어디까지 손대고 어디서 멈추는지 경계가 분명한 지점이었습니다.

### 환경 변수 — 더미 대신 실제로 쓰는 값으로

슬라이드는 `VITE_API_URL=https://api-stage.skcc.com` 같은 예시를 주는데, 이 앱에는 그런 서버가 없습니다. 그대로 넣으면 **아무 데서도 안 읽는 값**이 하나 생길 뿐입니다.

마침 `weatherApi.js`에 주소가 박혀 있었습니다. 그 자리를 환경 변수로 바꿨습니다.

```js
// 전
baseURL: 'https://api.openweathermap.org'

// 후
const BASE_URL = import.meta.env.VITE_API_URL || 'https://api.openweathermap.org'
```

`||` 기본값을 둔 것은, 개발용 `.env`에 이 값이 없어도 지금까지처럼 그냥 돌아가게 하기 위해서입니다.

`.env.staging` / `.env.production` 두 파일에는 `VITE_API_URL`과 `VITE_APP_MODE`를 넣었고, 빌드 스크립트를 나눴습니다.

```json
"build:staging": "vite build --mode staging",
"build:production": "vite build --mode production"
```

실행하면 어떤 환경 파일을 읽는지 터미널에 그대로 찍힙니다.

```
> vite build --mode staging
vite v8.2.2 building client environment for staging...
```

**`.gitignore`가 중요합니다.** `.env*`를 통째로 막아두면 새로 만든 두 파일도 같이 막힙니다. 그렇다고 규칙을 느슨하게 풀면 키가 든 `.env`가 새어 나갈 길이 생깁니다. 기본은 전부 막고, 비밀 값이 없는 셋만 예외로 뚫었습니다.

```
.env
.env.*
!.env.example
!.env.staging
!.env.production
```

`VITE_APP_MODE`는 푸터에 표시합니다. 배포하고 나면 **지금 보고 있는 게 방금 올린 그 빌드인지** 확인할 방법이 없어서, 캐시된 옛 화면을 보며 안 고쳐졌다고 착각하기 쉽습니다.

```
Vue 3 · Vue Router · Pinia · Vite · Production
```

dist/assets/index-DhxIp5Wk.css     54.71 kB │ gzip:  9.51 kB
dist/assets/index-CPWw2sdj.js     145.45 kB │ gzip: 52.32 kB
dist/assets/WeatherMap-DgC_KuX3.js 150.10 kB │ gzip: 44.19 kB

지도(Leaflet)가 별도 파일로 떨어져 있습니다. 과제 4에서 라우터에 지연 로딩을 걸어둔 결과로, 상세 페이지에 들어가기 전까지는 저 150KB를 받지 않습니다. 첫 화면에서 가장 무거운 덩어리가 첫 화면에 안 실리는 셈입니다.

파일명 뒤의 해시(`index-CPWw2sdj.js`)는 내용이 바뀌면 같이 바뀝니다. 브라우저가 옛 파일을 캐시해두고 새 화면을 안 보여주는 문제를 막는 표준 방식입니다.

### 배포 — Vercel

GitHub 저장소를 Vercel에 연결해서 `main`에 push할 때마다 자동으로 빌드·배포되게 했습니다. 빌드 명령과 출력 폴더는 Vite 기본값 그대로고, 손댄 것은 두 가지입니다.

**SPA 폴백** — `/weather/city_01`처럼 라우터가 만든 주소로 **바로 들어오면** 정적 호스팅은 그 경로에 해당하는 파일을 찾다가 404를 냅니다. 과제 4에서 만든 주소들이 새로고침이나 링크 공유에서 전부 깨지는 셈입니다. 모든 요청을 `index.html`로 넘겨 라우터가 경로를 해석하게 했습니다.

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

정적 파일이 실제로 있으면 그쪽이 먼저 응답하므로 `/assets/*.js`는 영향을 받지 않습니다.

**환경 변수** — `.env`는 저장소에 없으므로 Vercel이 빌드할 때 키를 알 방법이 없습니다. `VITE_OPENWEATHER_KEY`를 프로젝트 설정에 넣었습니다. 반면 `VITE_API_URL`은 `.env.production`이 저장소에 있어서 넣지 않았습니다. 양쪽에 다 두면 어느 쪽이 이기는지 헷갈리는데, Vite는 실행 환경에 이미 있는 변수를 `.env` 파일보다 우선합니다.

### 배포하고 나서야 보인 것 — 위치 권한

배포한 주소를 열어보니 화면보다 **권한창이 먼저** 떴습니다.

```
skala-vue-r5p7.vercel.app에서 다음 권한을 요청합니다.
📍 내 위치 확인
```

`AppShell.vue`의 `onMounted`에서 `detectMyLocation()`을 바로 부르고 있었기 때문입니다. 개발할 때는 이미 허용해둔 상태라 한 번도 못 봤고, 배포하고 남의 입장에서 처음 열어보고 나서야 보였습니다.

브라우저 권한창은 "내 위치 확인"이라고만 말할 뿐 **무엇에 쓰는지 설명해주지 않습니다.** 용도를 모르는 상태에서 위치를 내주는 사람은 없으니 대개 거절로 끝나고, 브라우저는 한 번 거절한 사이트에 다시 묻지 않으므로 그 뒤로는 설득할 기회조차 없어집니다. 자동으로 묻는 쪽이 오히려 기능을 잃는 구조였습니다.

그래서 묻기 전에 먼저 밝히고, 요청은 사용자가 눌렀을 때만 나가도록 바꿨습니다.

```
지금은 서울 기준입니다.  [ 📍 내가 있는 곳의 날씨로 보기 ]
```

이제 첫 화면에는 권한창이 뜨지 않습니다. 버튼을 누른 사람은 자기가 무엇을 허용하는지 알고 누르는 것이고, 거절하거나 실패했을 때도 "다시 시도"가 남아 있어 되돌릴 수 있습니다.

### API 키는 숨겨지지 않습니다

과제 조건이 "API 키는 환경 변수로 조정하고 Git에 업로드되지 않도록"이라 그대로 지켰습니다. `.env`는 `.gitignore`에 있고, 히스토리 전체를 뒤져도 키가 나오지 않습니다.

다만 **빌드 산출물에는 키가 그대로 들어갑니다.** 확인해보면 `dist/assets/index-*.js` 안에 32자리 키가 평문으로 박혀 있습니다.

당연한 결과입니다. `VITE_` 변수는 빌드할 때 **문자열로 치환**되고, 브라우저가 OpenWeatherMap을 직접 부르려면 그 키를 갖고 있어야 합니다. 환경 변수는 **키를 저장소에서 빼는** 도구지 브라우저에서 숨기는 도구가 아닙니다.

진짜로 숨기려면 서버를 하나 두고 브라우저 → 내 서버 → OpenWeatherMap으로 중계해야 합니다. 프론트엔드만으로는 방법이 없습니다. 그래서 실무에서는 **공개돼도 피해가 적은 키**(호출 도메인 제한, 무료 등급, 주기적 교체)를 쓰는 쪽으로 갑니다. `dist/`를 `.gitignore`에 넣어둔 것도 같은 이유입니다.

**느낀점**: 환경 변수는 그냥 "보안을 위해 쓰는 것"이라고 뭉뚱그려 알고 있었습니다. `.env`에 넣고 `.gitignore`에 걸어두면 키가 안전해지는 거라고 생각했는데, 빌드하고 나서 `dist/assets/index-*.js`를 열어보니 `appid` 자리에 제 키가 그대로 박혀 있었습니다. 잠깐 설정을 잘못한 줄 알았는데, 생각해보니 브라우저가 OpenWeatherMap을 직접 부르는 구조라 키가 브라우저 안에 없으면 아예 동작할 수가 없었습니다. `VITE_` 변수는 빌드할 때 문자열로 바꿔치기되는 것뿐이었습니다. 환경 변수가 지켜주는 건 **저장소**지 브라우저가 아니라는 걸, 산출물을 직접 열어보고 나서야 정확히 알았습니다. 진짜로 가리려면 서버를 하나 끼워야 하는데 그건 프론트엔드 바깥의 이야기였습니다.

ESLint를 처음 돌렸을 때 `'ElMessage' is not defined` 에러가 8개 났던 것도 같은 결에서 이해가 됐습니다. 빌드는 멀쩡히 되는데 lint만 실패하니 처음엔 설정이 꼬인 줄 알았습니다. 원인은 과제 7에서 붙인 자동 임포트가 `import` 구문을 빌드 시점에 끼워넣는다는 것이었습니다. 제가 보는 소스와 브라우저가 받는 코드가 같지 않다는 걸, 그 둘을 각각 읽는 도구가 서로 다른 말을 하고 나서야 체감했습니다. 개발할 때는 이 차이가 안 보이다가 빌드하고 배포하는 단계에서야 드러난다는 게 이번 회차의 핵심이었던 것 같습니다.

Prettier에서도 비슷한 경계를 봤습니다. `singleQuote`를 켜뒀는데도 백틱은 끝까지 안 바뀌길래 설정이 안 먹나 했는데, 백틱은 따옴표의 한 종류가 아니라 템플릿 리터럴이라는 다른 문법이었습니다. 바꾸면 서식이 아니라 코드를 고치는 게 되니 손대지 않는 것이었습니다. 도구가 어디까지 해주는지를 알고 쓰는 것과 알아서 해주겠거니 하고 쓰는 것은 다르다는 생각이 들었습니다.

## 공통: 디자인 시스템과 앱 셸

과제 4(라우터)부터 화면이 여러 개로 늘어나기 때문에, 화면을 하나씩 예쁘게 칠하는 대신 토큰과 셸을 먼저 잡았습니다. 원래 디자인이 전공이기 때문에 저만의 차별화 점이라는 맥락에서 추가하였습니다.

- **디자인 토큰 (`src/assets/tokens.css`)**: 색·타이포·간격·모서리·그림자를 CSS 변수로 한 곳에 모았습니다. 컴포넌트는 `var(--sk-...)`만 참조하므로, 톤을 바꾸려면 이 파일 하나만 고치면 됩니다. 정리 전에는 `#42b883`(Vue 기본 초록)이 11곳, `#1568b8`(파랑)이 9곳에 복붙되어 있어서 브랜드 색이 무엇인지 불분명했습니다.
- **2층 구조**: 헤더·히어로는 **시간대에 따라 바뀌는 하늘 그라데이션**(새벽/한낮/해질녘/밤)으로 날씨 앱다운 분위기를 주고, 본문 카드는 항상 **중립 회색 서피스**로 고정했습니다. 감성은 위층에, 데이터는 아래층에 두어 정보가 늘어나도 읽기 부담이 없도록 한 선택입니다.
- **색의 역할 분리**: 선택된 카드는 파랑(브랜드색), 검색어와 일치한 카드는 앰버로 구분했습니다. 원래는 둘 다 초록이라 "선택된 것"과 "검색에 걸린 것"이 같은 색이었습니다.
- **앱 셸 (`src/components/layout/AppShell.vue`)**: 브랜드·내비게이션·히어로·본문·푸터 골격을 컴포넌트로 분리하고 `#nav` / `#actions` 슬롯을 열어뒀습니다. 먼저 만들어 둔 덕에 과제 4에서는 `#nav`의 탭 버튼을 `<RouterLink>`로 갈아끼우고, 과제 5의 ℃/℉ 토글은 `#actions`에 꽂는 것으로 끝났습니다. 셸 자체는 두 번 다 손대지 않았습니다.
- 숫자(온도)에는 `font-variant-numeric: tabular-nums`를 적용해서, 값이 바뀌어도 카드 폭이 흔들리지 않게 했습니다.
